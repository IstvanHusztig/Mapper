# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

dMapper started as a standalone extraction of the LiDAR odometry (step 1) application of the HDMapping (hd-mapping) repository. It is a C++20 CMake project that builds a single executable, `dMapper`, which computes LiDAR+IMU odometry from a recording folder (lidar*.laz + imu*.csv). All dependencies are vendored under `3rdparty/` (Eigen, freeglut, LASzip, oneTBB, Fusion AHRS, imgui, manif, nlohmann json, observation_equations, portable-file-dialogs, a CSV parser in `csv-parser`, doctest). The code dMapper took over from HDMapping's shared `core` library lives in the layer folders; `core/` itself was retired (roadmap step 11) — no package manager, no network needed. Only OpenGL/GLU must come from the system.

**Priorities:** dMapper is a mapping application (target: cave surveys hundreds of metres long), so precision and map quality come before speed. When a choice trades one against the other (a slower but more robust method, more registrations, an extra solve), take the more precise one, and report the time cost instead of avoiding it.

**Documentation:** `docs/` is one guide: the user guide `docs/index.html` and a map of every page in `docs/README.md` and in the guide's "All documents" section (`#documents`), grouped by purpose. Every page carries the top line `dMapper docs › <group> · All documents` (class / comment `docs-nav`) and ends with "See also". The basic terms (pose, node, window, term, bend …) are defined once, in the guide's Fundamentals (`index.html#fundamentals`, one anchor `#t-<term>` each); a page links them (its "Terms used here" line under the lead, and inline in the guide) instead of defining them again, and a new term goes there first. A new page goes into both maps and gets the top line, the terms line and "See also"; after adding or changing a page, run `python tools/build_docs_index.py` (rebuilds the search index `docs/search-index.js` and the contents at the front of `docs/index.html`; `--check` finds them stale); `docs/agents/` (the Codex agents' notes) is listed but not edited. The Hungarian pages (`docs/hu/`) are updated only at the end of a body of work, not with each English change.

There are no linters or CI. Unit tests use doctest (`3rdparty/doctest`), and refactors are checked against a golden baseline (see Testing). Mechanical renames in refactors are done with `tools/rename_identifiers.py` (code only, never comments or strings; `-m` for member accesses only; `--dry-run` first).

**Missing tools:** when a tool or package an analysis needs is missing (a Python module such as numpy, a CLI program), ask the user to install it (name the package and the command, e.g. `python -m pip install --user numpy`) instead of working around it with a slower or weaker substitute or reporting it as a blocker. Repo tools in `tools/` stay pure Python unless a change decides otherwise.

**Keep tool output small:** Bash results cost context. Pipe command output through `head`, `tail` or `grep` to reduce its size (build and run logs go to a file, then only the relevant lines are shown), and avoid `cat` on large files — use Read with offset/limit instead.

## Build

Requires CMake >= 4.0. `CMakePresets.json` defines exactly two configurations, `x64-Release` and `x64-Debug` (Ninja + cl, build trees `out/build/<preset>`); Visual Studio uses them via Open Folder. Do not add other build trees. Exception: the region agents' standing worktrees (`C:/Repo/dMapper-worktrees/region-a`, `region-b`)
each have their own `out/build/x64-Release` from the same preset (see Regions). From a shell, `vcvars64.bat` must be loaded first (cl/ninja on PATH):

```
cmake --preset x64-Release
cmake --build --preset x64-Release --target dMapper
```

- Output: `out/build/<preset>/bin/dMapper.exe` (the name is `APP_NAME` in `CMakeLists.txt`). On Windows, runtime DLLs (TBB etc.) and `settings/default_settings.toml` are copied next to the exe post-build. Debug is unoptimized and many times slower; always process data with Release.
- `-DHD_CPU_OPTIMIZATION=AUTO|INTEL|AMD|ARM|GENERIC` selects release optimization flags (AMD on MSVC adds `/Oi /Ot /Oy`). MSVC Release builds use `/fp:precise` everywhere, so results do not depend on how the compiler orders sums.
- dMapper's version (`DMAPPER_VERSION_MAJOR/MINOR/PATCH`, now 0.1.0) is defined in the root `CMakeLists.txt`; `src/domain/dmapper_version.h` turns it into `dmapper_version()` ("0.1.0") and `dmapper_version_short()` ("0.1", the GUI title) and errors if it's missing. The output folder's `dMapper_params_<version>_<date-time>.toml` and `dMapper_results_<version>_<date-time>.json` carry it in their names, and they and `session.mjs` (`lidar_odometry_version`) carry it inside. A loaded TOML's `[version_info]` only feeds the compatibility warning (major and minor must match); a run records the build's version.

## Testing

- **Debug builds only when they can matter, and only after asking:** build and test with `x64-Release` only. Never start a Debug build (the orchestrator or any agent) without first asking the user explicitly and naming the cause; an agent that thinks one is needed says so in its hand-back instead. The candidates are changes that can behave differently there: asserts or `NDEBUG`-dependent code, uninitialized or out-of-bounds memory, iterator/container debug checks, undefined behaviour, threading or lifetime changes, build-system or compiler-flag changes. Not for settings, docs, tests of pure maths, renames or other changes that cannot depend on the configuration. Say in the task result which configurations were run.
- **Unit tests:** `cmake --build --preset x64-Release --target lidar_odometry_tests`, then `ctest --test-dir out/build/x64-Release` (vcvars loaded). Tests live in `tests/` and must run without recorded data or a display. They link the layer libraries (`lo_infrastructure`, which brings `lo_application` and `lo_domain`). `tests/scan_to_map_test.cpp` runs `optimize_lidar_odometry` on a synthetic room and corridor against the true trajectory, with maps built with the exact NDT cell statistics, and checks that its parallel node loop gives the same result as a sequential one, bit for bit. `tests/ndt_map_test.cpp` tests `update_rgd` itself in both modes. `tests/synthetic_recording.{h,cpp}` (namespace `synthetic`) holds the shared scene helpers and the loop recording (two laps around a block, 44 windows, turn rate ramped in the corners), and `tests/memory_point_store.h` an in-memory `PointStore`. The truth tests of `consistency-harness`: `tests/truth_statistics.{h,cpp}` (normalised error, chi-square quantiles, the number of runs for a stated power, a platform-stable `Rng`), `tests/synthetic_inertial.{h,cpp}` (analytic motion with truth, IMU samples in the estimator's own time conventions: gyro sample k = the interval ending at node k, accelerometer sample k = the interval starting at it; noise, gyro bias and acceleration offset as the weights claim) and `tests/synthetic_routes.{h,cpp}` (routes R1 loop, R2 out and back through a corridor with a blind middle, R3 rest-walk-rest; points stamped just after their node; a `RecordingSource` that filters like the production one; `cut_into_windows` through the real `load_data`, `calculate_trajectory`, `compute_step_1`); on them the fixtures F-a…F-e and K8 (`terms_at_truth_test.cpp`, `accelerometer_noise_test.cpp`, `window_covariance_test.cpp`, `unit_cases_{inertial,ndt}_test.cpp`, `loop_chains_test.cpp`, `lidar_claim_test.cpp`): a smoke case each in `ctest`, the measured sets `doctest::skip` (run with `-tc="window covariance*" --no-skip -s` etc.); how to make a recording and which claim each file checks: `docs/regions/verification.md` (How to check your work). `tests/consistency_test.cpp` runs `run_consistency` in both variants on it. `tests/orientation_test.cpp` runs `calculate_trajectory` against a recording fake `OrientationEstimator`, and `tests/serial_executor.h` is a `ParallelExecutor` for tests. `tests/gui_view_model_test.cpp` drives the GUI's view-model without a display (settings and their source, a run that can't start or fails to load, Pause/Resume). `tests/loop_closure_test.cpp` runs `run_loop_closure` on it, but its cases are `doctest::skip()` (about 20 s each in Release, more than 15 min in Debug): run them to debug the loop closure with `lidar_odometry_tests -tc="loop closure*" --no-skip -s`. A case marked `doctest::should_fail` records a known shortcoming with its cause in a comment; when it starts to pass, doctest reports it, and the marker goes.
- **Golden baseline:** a pure refactor is compared with `tools/compare_baseline.py`:
  - `44_short` must be bit-identical with `tools/baseline/44_short.manifest.json`; check it on every intermediate commit (about 1.5 min).
  - The full 44 runs once per change (about 20 min with `imu_always_on`). It must be bit-identical with `tools/baseline/44.manifest.json`. A change that deliberately alters numbers (a new algorithm, a compiler flag) measures its effect first (`--tolerance` against the old baseline folder `raw data/44_baseline`, `tools/eval_odometry.py`) and then sets new baselines in its own commit: the manifests, and the folders `raw data/44_baseline` and `raw data/44_short_baseline` (the old ones renamed with a date suffix). The datasets are in `C:\Users\User\Downloads\dLidar\raw data\` (`44_short` was made with the `cut_recording` target). Recording 44's IMU timestamps were corrected on 2026-10-09 (they lagged the LiDAR by 50–80 ms; `tools/restamp_imu.py`, measured with `tools/imu_time_offset.py`). The unsynchronized originals (35, 42, 43, 44's original IMU file) are in `C:\Users\User\Downloads\dLidar\unsynced_archive` and must not be processed. Run Release with `settings/l2-vertical.toml`, and never run two jobs on the same input folder at once (they share its `cache/`). See `tools/README.md`.

- **Position check between two results:** `tools/trajectory_seams.py <reference> <result>...` prints the largest position difference, when it first exceeds 5/20/50 cm and the longest stretch above (yaw-only `eval_odometry.py` doesn't see a lagging stretch, which draws a ghost wall where the path passes the same place again). A change to the odometry's numerics is also run with a `/fp:fast` build of the same code (a scratch worktree with `/fp:precise` replaced, built outside the presets) and the two compared this way: a large difference means a fragile decision somewhere (change `odometry-stall-fix`). `log_window_diagnostics` prints one line per window to find it.
- **Wall pairs from poses:** `tools/wall_pairs.py freeze` stores the returns of a result's wall pieces once; `measure <set> <trajectory>...` gives the gap between two visits of each wall for any trajectory of that recording (result, loop closure replay, odometry snapshot) in seconds, without a cloud. It is agreement between visits on the frozen set, not accuracy; freeze the set before the variants run. `run_health.py` also reports the stage durations and the number of windows stopped at the time limit.
- **Map quality:** a change to the odometry, the map, loop closure or consistency is judged with `tools/map_quality.py` on s0, s1 and s2 of recording 44 against the noise floor of the unchanged code: global geometry (façade angle start vs gallery), consistency (revisits, doubled walls) and sharpness (jitter; `--floors` for railing and stairwell), all three of equal weight; it counts only beyond the s0/s1/s2 spread, and it must not widen that spread. The code-review findings and their status are in `docs/code-review-tracker.md`.
- **Subagents:** Claude may start subagents on its own when it sees a need, without asking first. Good candidates are long, self-contained jobs with a small result, such as a full 44 evaluation (runs, CloudCompare export, `eval_odometry.py`, counting log lines) or a broad code search. Give the subagent the exact scripts, paths and pass criteria, and check what it reports before acting on it.

## Regions

The code is divided into eight regions (front-end, map, lidar-matching, inertial, solver, back-end, noise-budget,
verification), each with an owner agent (`.claude/agents/region-<name>.md`) and a knowledge file
(`docs/regions/<name>.md`: contract, files, how to check, known flaws, experiments, ideas rejected, open questions). The
main session is the orchestrator: it owns what the regions share, talks to the user, starts the agents and decides what is
merged. `docs/regions/README.md` has the rules and the protocol; in short:

- **Who owns what:** `docs/regions/owners.toml` (files, `file::function` entries, shared test files; the unnamed rest is
  the orchestrator's). `python tools/region_owners.py` checks it; `--diff <base>..<branch> --region <name>` lists what a
  branch touches outside its region.
- **Worktrees:** an editing agent works in a standing worktree (`C:/Repo/dMapper-worktrees/region-a` or `region-b`, reset
  to the main tree's commit before each job) on its own branch `region/<name>/<date>-<question>`, and hands the branch
  back. At most two editing agents at once. Agents never merge, push, start full runs or change `settings/`.
- **Merge:** the orchestrator checks the branch (ownership, `tools/step_checks.py` in the worktree, the conclusion
  reviewer), then merges a branch that changes no number on its own judgment and one that changes a number only after the
  user's decision on its numbers; after each merge `tools/step_checks.py` runs on the main tree.
- **Verification kit:** `tools/step_checks.py` (build, tests, both guards, both replays, the per-term table, 44_short;
  about 7 min; `--record` writes the references), `tools/end_runs.py` (full 44, Livox 3, 44_short against their
  manifests, `--debug`; about 50 min, background), `tools/run_replay.py` (the gate every replay goes through: memory and a
  slot, its cost, the time-limit count). Paths in `tools/local_paths.toml`; captures and references in
  `C:/Users/User/Downloads/dLidar/experiments/guards/`.
- **Knowledge files** are written by the orchestrator from the agents' hand-backs, after review and, where a number or a
  contract changes, after the user's decision.

## Run

- **Headless / CLI:** `dMapper <input_folder> <params.toml> <output_folder>`. Exactly 3 args triggers batch mode. The settings are the built-in defaults plus `<params.toml>` only, never a `default_settings.toml` from the working directory; an unreadable TOML exits 1.
  - **Reprocessing from an odometry snapshot:** with `save_odometry_snapshot = true` a CLI run writes `odometry_snapshot.bin` to the output folder after the odometry. `dMapper <input_folder> <params.toml> <output_folder> --from-snapshot <file>` then loads the recording, takes the windows from the snapshot instead of running the odometry, and runs loop closure, consistency and saving: minutes instead of half an hour, for loop-closure experiments. The snapshot is refused if the odometry settings (every TOML setting outside `[loop_closure]`, `[consistency]`, `[lidar_odometry_debug_info]`, `[paths]`, `[misc]`, `[version_info]`) or the windows' timestamps differ. Reader and writer: `src/infrastructure/odometry_snapshot_file.{h,cpp}`.
  - **Window capture and replay** (for one stretch of a recording): with `capture_windows_from_s` / `capture_windows_to_s` (`[lidar_odometry_debug_info]`, seconds from the first window's start, as `time_s` of `log_window_diagnostics`) a CLI run writes `window_capture_<from>-<to>s.bin` to the output folder: the window loop's state before the range (NDT maps, run state, `WindowLoopCarry`), the windows and their points, and each window's iteration count and final poses. `dMapper --replay <file> <params.toml>` runs only that range again. With the capture's own odometry settings the iteration counts are forced (no time limit) and every window must come out bit for bit (exit 1 if not); with other settings it reports how far the windows move, starting from the run's own map, so an idea is screened in seconds and confirmed by a full run. Port `src/application/window_capture.h`, replay `window_replay.{h,cpp}`, file `src/infrastructure/window_capture_file.{h,cpp}`; the loop runs any range through `process_windows` (`window_loop.h`). A capture of 21 windows of 44_short is 73 MB.
  - **Loop closure capture and replay** (for loop closure settings): with `capture_loop_closure = true` (`[lidar_odometry_debug_info]`, outside the settings hash; `capture_loop_closure_max_tries` bounds the tries kept) a CLI run, also one with `--from-snapshot`, writes `loop_closure_capture.bin` to the output folder: the windows as the odometry left them, the segments, and every registration the loop closure tried (transform, overlap before and after, information, correction). `dMapper --replay-loop-closure <capture> <params.toml> <output_folder>` runs only what follows the registrations (`close_loops` in `src/application/loop_closure.h`: edge choice, pose graph, pruning, node correction) and writes the trajectory and the loop log, without the recording. With the capture's own settings every node must come out bit for bit (exit 1 if not); with other loop closure settings it chooses among the recorded tries, and names the missing ones (another candidate, search range or segment length) and writes nothing. The capture holds no points, so a rule is screened in seconds and confirmed by a full run. Refused: the odometry settings, `loop_closure_segment_windows`, `loop_closure_max_correction_m`, `loop_closure_cross_floor_search_m`. Port `src/application/loop_closure_capture.h`, replay `loop_closure_replay.{h,cpp}`, file `src/infrastructure/loop_closure_capture_file.{h,cpp}`, CLI `src/presentation/cli/loop_closure_replay_cli.cpp`.
  - **Per-term window table** (which term holds a window back or pushes it away): with `log_window_terms = true` (`[lidar_odometry_debug_info]`, outside the settings hash) the loop computes, at each window's guess and result, every term's cost, residuals, and weight and pull for four motions (shift, stretch, curve, turn) along travel, sideways and vertical (`src/domain/window_term_table.{h,cpp}`, built from the term functions on their own equations; it changes no result). One `window terms` log line per window; a CLI run writes `window_terms.csv` and `window_features.csv` to the output folder, `--replay` writes `<params name>_window_terms.csv` / `_window_features.csv` next to the capture (port `src/application/window_term_sink.h`, files `src/infrastructure/window_term_csv.{h,cpp}`). `tools/window_terms.py` prints a window's table or a per-term summary of a range. The pull is one linear step with everything else held (NDT reaches about 85 % of a 1 cm offset); about 9 % more replay time with it on. The record of a window is completed after its hand-off and written once (`finish_window`): `window_features.csv` also holds the state the window was prepared with (first pose, priors with their sigmas) and what it handed on (end velocity, gravity vector after the fold, offset and bias with sigmas, the last node as solved and after the tail re-propagation, `handoff = done | cancelled`), the mean rotation rate and the start acceleration (`prepared_*`, `handed_*` columns, consistency-harness D9).
  - **Noise model log:** every run and replay logs one `noise budget` line (the constants the settings give: sigmas before time scaling, accelerometer noise, random walks, scales); `log_window_noise = true` (`[lidar_odometry_debug_info]`, outside the settings hash) adds a `window noise <n>:` line per window with its noise model as sigmas, and with `log_window_terms` the same values are `noise_*` columns of `window_features.csv`. Results unchanged.
  - **Window verdict** (`src/domain/window_verdict.{h,cpp}`): after each window, `report_window` judges it: readings (heading, roll and pitch bend against the gyro, speed, gyro bias, velocity chi², information ratio, why the iterations stopped and the solver's events; with `log_window_terms` the remaining step and the LiDAR's weight share) and four flags with the agreed limits (bent > 3°, bent severely > 10°, fast > 2.5 m/s, bias high > 0.5 °/s). A reading a window doesn't have is NOT MEASURED. Every run, replay and cancelled run logs a `window verdict summary` (counts, coverage, the contract's run triggers: more than 1 % bent, any other flag, the chi² median / p95 of the weak windows); `log_window_verdict = true` adds a `window verdict <n>:` line per flagged window, and with `log_window_terms` the flags and readings are columns of `window_features.csv`. It also gives three **normalised moves** (start velocity; start velocity and offset jointly with the joint prior; gyro bias): the move from prior to result against the covariance that move has under the window's own model, q = d^T P^-1 d / (n - tr(P^-1 P_post)), expected value 1, descriptive, NOT MEASURED where the covariance is missing or unusable, the last step was still large, the bias is clamped or the window adds too little (trace reduction below 0.5); the summary lists largest, median, p95 and coverage, without limits or triggers. The velocity chi² is unchanged (consistency-harness D10). Investigation triggers, not a statement about the map (`openspec/changes/sensor-neutral-yardstick/criteria-proposal.md`); it changes no result.
- **GUI:** any other argument count opens the freeglut + ImGui window, titled "dMapper v 0.1" (`winTitle` in `lidar_odometry_gui.cpp`, from `dmapper_version_short()`). The menu bar has Start, View and Camera:
  - **Start → 1. Load parameters…** loads a TOML. This is the only way to change settings in the GUI; at start-up it loads `default_settings.toml` from the exe folder. The Start menu and the progress window show the active parameter file.
  - **Start → 2. Load data and process…** (Ctrl+O) picks the recording folder, then loads it on a worker thread, processes it with the same stages as the CLI, and saves `lio_result_<n>`. For the same input and settings the result is identical to the CLI's.
  - **View** has Show point cloud, Show trajectory, compass/ruler and Lock Z; **Camera** has the fixed views and orthographic projection.
  - **Live point cloud preview** (`PreviewCloud` in `lidar_odometry_gui.cpp`):
    - built on the main thread from data the run already keeps: each window the odometry has reported done (`GuiProgress::windows_done()`) is read through `OdometryPipeline::load_window_points` and placed with its optimized trajectory;
    - thinned to 0.10 m voxels across all windows and coloured by height, at most 4 windows per frame;
    - rebuilt once from the final trajectory after the run (after loop closure and consistency);
    - it never changes processing or results.
  - **Trajectory** (`TrajectoryCopy` in `lidar_odometry_gui.cpp`): drawn from a main-thread copy of node positions, never from poses the run may still change. During the odometry it grows with the windows reported done (the red cross marks the last finished pose); during loop closure, consistency and saving it stays; after the run it is rebuilt from the final trajectory, together with the preview.
  - **Reading a run's windows:** the view reads them only inside `GuiProgress::read_finished_windows`, which runs its reader under a lock that `stage_started` takes too, and only while the stage is Odometry. The run announces each post-processing stage before it writes a pose, and `optimize_windows` reports a window done only after the last step that can change it, so the windows read there are final until the run ends.
  - The progress window shows the current stage (Loading, Odometry with percentage and estimate, Loop closure, Consistency, Saving) and can pause the run.
  - The window redraws on a timer (`schedule_redraw`): about 10 frames per second during a run and 60 otherwise, so the redraw doesn't slow the processing. A slower run would change results through `real_time_threshold_seconds`.
  - The background colour comes from `[misc] clear_color` in the loaded TOML.
  - There are no settings widgets, presets, georeferencing, or export/editing tools. Georeferencing is meant to be a separate post-processing module.

The input folder is scanned non-recursively. `pair_recording_files` (`src/infrastructure/recording_files.cpp`) sorts the files and splits them by extension (`.laz`/`.las` point clouds, `.csv` IMU data); everything else is ignored. LAZ and CSV files are paired by sorted order, and each must have a partner with the same last four characters of the name. There is no multi-LiDAR calibration: points are only shifted by the lever arm (`lidar_imu_lever_arm_*`).

## Architecture

Target architecture (Clean Architecture, layers, ports, migration roadmap) is in `docs/ARCHITECTURE.md`; refactors should move the code toward it, and new code and refactors respect the SOLID principles (its section 7). What follows describes the current code.

**Layers:** the code is in `src/`, one folder per layer, each built as a static library whose include directories admit only what the layer may use. A file that includes something its layer must not see doesn't compile:
- `src/domain` → `lo_domain`: entities and optimizers (`window.h`, `ndt_map`, `scan_to_map`, `normal_equations`, `imu_kinematics`, `window_steps`, `optimizer_options`), plus `odometry_config.h`, `odometry_state.h`, `angle_units.h` and the `Logger`/`ProgressReporter` interfaces (`run_reporting.h`). Only Eigen, manif and observation_equations. Also the value types and pose conversions taken over from HDMapping's `core` (`structures.h` with `Point3Di`, `TaitBryanPose`, `LaserBeam`, `Plane` …; `transformations.h`; `ndt_types.h`; `point_placement.h` with `points_to_vector`), unchanged; `structures.h` still holds HDMapping structs dMapper doesn't use.
- `src/application` → `lo_application`: the ports (`input_ports.h`, `output_ports.h`, `service_ports.h`) and the use cases (`odometry_pipeline`, `lidar_odometry`, `run_odometry`, `loop_closure`, `consistency`). Nothing third-party beyond the domain's: Fusion and TBB don't compile here. (A bare `#include <Fusion.h>` does, because the Windows .NET SDK has a header of that name; use `<FusionAhrs.h>` to check.)
- `src/infrastructure` → `lo_infrastructure`: the adapters (folders, LAZ, CSV, TOML, JSON, console, the Fusion AHRS, the TBB executor), with the include directories of those libraries only (no ImGui, GLUT or GL). `laz_export.{h,cpp}` writes LAZ files (`exportLaz`, from `core`'s `export_laz.h`, unchanged); the CSV parser is `3rdparty/csv-parser/csv.hpp`.
- `src/presentation/cli` (`run_cli`), `src/presentation/gui` (`run_gui`, `lidar_odometry_gui.cpp`) and `src/main.cpp`, the composition root that picks one by the argument count. The GUI's state and actions are in `GuiViewModel` (`src/presentation/gui/gui_view_model.{h,cpp}`), built as `lo_gui_view_model` with only the infrastructure's include directories, so ImGui, GLUT and GL don't compile there and the tests can link it.
- The GUI's viewer is `src/presentation/gui/viewer.{h,cpp}` (camera, input, menus, axes, compass, `initGL`, and the camera globals such as `bg_color`, `lock_z`; from `core`'s `utils`, without its session picking and Info window), and its dialogs are `file_dialogs.{h,cpp}` (`mandeye::fd::OpenFileDialog`, `SelectFolder`, `OutOfMemMessage`; from `core`'s `pfd_wrapper`). Both are compiled into the exe.

**Pipeline:** `OdometryPipeline` (`src/application/odometry_pipeline.{h,cpp}`) owns one run's data (`points_per_file`, `imu`, `imu_trajectory`, `windows`, `state`) and runs the stages `load` (1–3) → `run_odometry` (4) → `post_process` (loop closure if `use_loop_closure`, then consistency if `use_consistency`) → `save` (5). The CLI branch of `main()` and the GUI (global `pipeline`) both use it:
1. `load_data` — read the LAZ chunks and IMU CSV through the `RecordingSource`, shift the points by the lever arm, and sort them.
2. `calculate_trajectory` — IMU-only orientation through the `OrientationEstimator` port (NWU/ENU/NED convention flags in params). The gyro-bias estimate, the gain switching and the time-step rules are in `calculate_trajectory`; the adapter `FusionOrientationEstimator` only wraps Fusion's AHRS. IMU samples are `ImuSample`s (`src/domain/imu_sample.h`, float vectors as read).
3. `compute_step_1` — cut the data into `Window`s (explained in `docs/PIPELINE.md`; `src/domain/window.h`: `poses`, `motion_model_poses`, `timestamps`, `imu_angles`, `imu_acc`, `gyro_bias`); each window's points go to the `PointStore`.
4. `optimize_windows` (`src/application/run_odometry.cpp`, the window loop) — per-window scan-to-map optimization against an NDT-bucket reference map (built by `update_rgd` in `src/domain/ndt_map.{h,cpp}`, with the cell types in `src/domain/ndt_types.h`; `use_exact_ndt_bucket_statistics` picks exact cell statistics over the previous ones, off by default, see `docs/degeneracy-information.html`): the Levenberg-Marquardt iterations are `lm_solve` (`src/domain/lm_solver.{h,cpp}`: the damping schedule, the convergence and time limits through callbacks, `lm_step_check`, and why the iterations stopped) over the window's `WindowProblem` (`src/domain/window_problem.{h,cpp}`), which linearizes, takes the covariance of the extra unknowns, applies a step and keeps snapshots; the solver knows no term and is tested on a two-unknown problem (`tests/lm_solver_test.cpp`). One iteration is `optimize_lidar_odometry` (`src/domain/scan_to_map.cpp`, one `lm_iteration`). The window problem's linearization calls one function per term in a fixed order, each adding to a `WindowEquations` (`src/domain/window_equations.h`: banded matrix, right-hand side, running motion cost, residual count): the NDT point terms per grid and the degeneracy projection (`ndt_term`), the motion-model edges with their `MotionEdgeWeights`, the gyro-bias prior and the velocity continuity (`motion_model_terms`), the accelerometer terms and the velocity and offset priors (`accelerometer_term`), and the origin fix, solve and step (`window_solver`); each term is tested on its own in `tests/window_terms_test.cpp`. The terms compute no weight: every weight of a window (motion edges, velocity continuity, accelerometer terms with their spans, the gyro-bias, start-velocity and acceleration-offset priors with their growth, zero velocity, origin fix, and the NDT term's per-point rules) comes from its `WindowNoiseModel` (`src/domain/window_noise_model.{h,cpp}`), built once per window by `build_window_noise_model` in `prepare_window` with the unknowns' layout, and read by the window problem, the per-term table and the weak-axis diagnostic; tested in `tests/window_noise_model_test.cpp`. The loop uses the IMU helpers in `src/domain/imu_kinematics.cpp` (world-frame acceleration, rest detection, gyro-bias removal, acceleration offset); the optimizers share the normal-equation helpers in `src/domain/normal_equations.cpp`. The loop body (`process_windows`) is four steps, `prepare_window`, `solve_window`, `report_window`, `finish_window`, sharing a `WindowWork`; the per-run settings are in `OdometryRunSetup` and what passes from window to window in `WindowLoopCarry`; the steps that only need window data (`place_window_after`, `place_windows_after`, `estimate_previous_velocity`, `predict_window_poses` with its steps `mean_shift_of` and `guess_window_translations`, the rest test `window_rests` that the accelerometer term and its diagnostic share, `apply_gyro_bias_prior`, `is_turn_window`, `repropagate_window_tail`) are in `src/domain/window_steps.cpp` and tested on synthetic windows, the others (accelerometer term, LM iterations, map update) are file-local in `run_odometry.cpp`. `optimize_lidar_odometry` takes the `Window` and named options from `src/domain/optimizer_options.h`: `ScanToMapOptions` and `MotionModelOptions` (built once per run by `get_scan_to_map_options` / `get_motion_model_options`) and `VelocityPrior` (the previous window's final velocity), plus the rotation and translation IMU options (`MotionModelRotationOptions`, `MotionModelTranslationImuOptions`, same header). Also an optional `Consistency` pass (`src/application/consistency.cpp`; `run_consistency`, run in `post_process` when `use_consistency = true`). Loop closure: `run_loop_closure` (`src/application/loop_closure.cpp`).
5. `save_result` (`src/application/lidar_odometry.cpp`) — concatenate the windows into output chunks, place the points and compute the relative trajectories, and hand everything to the `ResultSink`. It does no file I/O.

**Input I/O:** pipeline code has no file names, folders, LASzip calls or CSV parsing on the input side. It uses three ports from `src/application/input_ports.h`:
- `RecordingSource` reads the LiDAR + IMU chunk pairs.
- `PointStore` holds point sets between stages: each window's original and intermediate points, and the session chunks of `save_result`.
- `PreviewSink` writes `calibrationValidation.asc` and `temp_point_cloud_<i>.laz`.

`OdometryPipeline` owns them as `RunInputs`, built by `make_folder_inputs(files, logger)` (`src/infrastructure/folder_inputs.cpp`) for a recording folder. Next to them it owns `RunServices` (`src/application/service_ports.h`), built by `make_run_services()` (`src/infrastructure/run_services.cpp`): the `OrientationEstimator` (Fusion) and the `ParallelExecutor` (`TbbExecutor`, used by `load_data` to read the chunks). `load()` fails without either. There is one adapter for each input port:
- `RecordingFolderSource` (`src/infrastructure/recording_folder_source.{h,cpp}`, which also holds `load_imu` and `load_point_cloud`);
- `DiskPointStore` (`<folder>/cache/*.cache`, window files numbered from 0);
- `FolderPreviewSink` (`<folder>/preview`).

The pipeline records the cache and preview folders in `state.paths` from the ports' `location()`. **Output I/O and settings:** two ports from `src/application/output_ports.h`:
- `ResultSink` receives a finished run in a fixed order: point sizes, each chunk's cloud and `TrajectoryRow`s, the merged cloud, chunk poses, index poses, the `SessionSummary`, the parameters and the processing results.
- `ConfigRepository` loads and saves `OdometryConfig` + `RunPaths` + `GuiPreferences` by location.

Their adapters:
- `FolderResultSink` (`src/infrastructure/folder_result_sink.{h,cpp}`) holds every output file name and format: the LAZ files and the merged LAZ writer, the trajectory CSV, `.mri`/`.mrp`, `index_poses.json`, `session.mjs`, and the parameters TOML (written through its `ConfigRepository`), plus the results JSON. It also has `get_next_result_path` (the GUI's `lio_result_<n>`).
- `TomlConfigRepository` (`src/infrastructure/toml_config_repository.{h,cpp}`) wraps `TomlIO`.

`OdometryPipeline::save(ResultSink&, gui, elapsed)` writes a run. The CLI builds a `FolderResultSink` on `argv[3]`, and the GUI builds one on the next `lio_result_<n>`. The CLI, the GUI defaults and Start → Load parameters load settings, and `FolderResultSink` saves them, only through `TomlConfigRepository`; `TomlIO` is used only inside it.

**Reporting:** pipeline code never writes to the console and has no progress atomics or sleeps. It uses two ports from `src/domain/run_reporting.h`, passed in explicitly:
- `Logger` for messages: `log_info(logger) << ...`, also `log_debug`, `log_warning`, `log_error`. Each message has its own stream, so it sets its own precision.
- `ProgressReporter` for the stage (`RunStage`), progress within the stage, and `checkpoint()`, where a paused run waits.

`OdometryPipeline` takes both ports in its constructor and reports each stage. There are two adapters:
- `ConsoleReporter` (`src/infrastructure/console_reporting.{h,cpp}`) writes whole, thread-safe lines: info/debug to stdout, warning/error to stderr, a `[stage]` line per stage, and the loading counter. The CLI and the GUI both use it for messages.
- `GuiProgress` (`src/presentation/gui/gui_progress.h`) feeds the progress window and implements Pause/Resume.

Logging is console only; nothing is written to the output folder.

**Settings and state** (`src/domain/odometry_config.h`: `OdometryConfig`, `RunPaths`, `GuiPreferences`; `src/domain/odometry_state.h`: `OdometryState`). Every file includes what it uses; there is no catch-all header:
- `OdometryConfig` holds every setting and is passed `const&` to the pipeline. Only TOML loading (`ConfigRepository`) writes to it; the GUI has no settings widgets.
- `OdometryState` holds what a run produces: the NDT maps, `m_g`, the initial and reference points, the trajectory length, and `RunPaths` (the `[paths]` keys plus the cache folder). Functions that change it take it explicitly.
- `GuiPreferences` holds GUI-only values (`clear_color`, saved in `[misc]`).

GUI defaults are loaded by `GuiViewModel::load_default_parameters`, called by `run_gui` with `default_settings.toml` next to the exe; the CLI doesn't load it. TOML I/O (`src/infrastructure/toml_io.h`, used only by `TomlConfigRepository`) is table-driven and takes `(OdometryConfig, RunPaths, GuiPreferences)`. To make a new setting loadable and savable, add it to both `TomlIO::POINTERS` (name → `OdometryConfig` member pointer; only bool/double/int/string supported) and the right `CATEGORIES` section, then regenerate the golden TOML test files (`LO_UPDATE_GOLDEN=1`, in their own commit). `settings/default_settings.toml` is the shipped config.

**IMU rotation prior and gyro bias** (in `optimize_lidar_odometry` / `optimize_windows`, all on by default):
- `[motion_model_uncertainty]`: `use_time_scaled_rotation_sigma` replaces the constant `*_om/fi/ka_1_sigma_deg` with `max(rotation_sigma_inflation_k * gyro_arw_{x,y,z}_deg_sqrt_s * sqrt(dt), rotation_sigma_floor_deg)` per consecutive-node edge.
- `[gyro_bias_estimation]`: `use_gyro_bias_estimation` adds a 3-axis gyro bias to each window's unknowns (`Window::gyro_bias`, a `GyroBiasState` with `mean` and `covariance`), carried to the next window as a prior. The prior sigma starts at `gyro_bias_initial_sigma_deg_s`, grows by `gyro_bias_rw_deg_s_sqrt_s`, and the bias is clamped at `gyro_bias_max_deg_s`. `handoff_tail_nodes` re-propagates each window's last nodes from the IMU before they seed the next window (0 = off). The per-window bias is written to `gyro_bias_per_window` in the results JSON.
- Switching all three off (`false`, `false`, `0`) reproduces the previous behaviour. The IMU CSV timestamps must be strictly increasing.

**IMU always on** (`[imu_translation] imu_always_on`, on in `settings/l2-vertical.toml`, off by default): the accelerometer term in every window from the second on (`optimize_lidar_odometry`, the accelerometer term in `scan_to_map.cpp`): rotation coupling (a tilt is fixed in the attitude), start/end velocity unknowns (`Window::velocity`, a `VelocityState` carried like the gyro bias), the acceleration offset carried with `imu_acceleration_offset_rw_mps2_sqrt_s`, zero velocity in windows at rest, and a guess integrated from the accelerometer (`integrate_window_translations` in `window_steps.cpp`). Each term is weighted 1 / ((density² / τ + floor²) τ²): `imu_accel_noise_density_mps2_sqrt_hz` (0.0013, the L2 measured at rest) and the vibration floor `imu_accel_floor_sigma_mps2` (0.1). It replaced the degenerate gate (removed, with the older accelerometer term, in `remove-gated-accelerometer`) and removed the stalls in blind passages on the synchronized 44; it needs IMU and LiDAR timestamps that agree within a few ms, and costs about 1.85× the odometry time. Design and evidence: `openspec/changes/archive/*-imu-always-on/`.
- `tools/eval_odometry.py` (see `tools/README.md`) computes the trajectory and map-sharpness metrics used to validate changes here.

**No `core/` any more** (roadmap step 11, `retire-core`): dMapper used to build HDMapping's shared `core` library (sessions, point clouds, NDT, ICP, pose graphs, GNSS …) and used very little of it. What it used now lives in the layers (above); the rest, with its link-order rules, is in git history. GLEW, ImGuizmo, implot and glm went with it.

The GUI's state lives in a `GuiViewModel`: the settings and their source, the console, the `GuiProgress`, the current `OdometryPipeline`, the recording folder, the running flag and the worker thread. Its actions take paths, not dialogs (`load_parameters`, `start_run`, `clear_point_store` …), and the worker reports back through `RunNotifier`, which the GUI implements with its message boxes. Because GLUT callbacks take no user data, `lidar_odometry_gui.cpp` keeps one file-scope pointer, `view_model`, set in `run_gui`, plus pure view state (`show_trajectory`, `show_point_cloud`, the preview cloud, the redraw flag). The viewer's camera and view globals (`viewer.h`) are still globals, as in the code they came from. The CLI (`run_cli`) uses only locals.
