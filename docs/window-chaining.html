Window chaining: what was wrong, and what the fix changed

Change chain-next-window-only, October 2026. After every window, the odometry loop used to place all later windows again, although only the next one is ever read. This page explains the old code, why that work was wasted, what replaced it, and what it gained, with measurements.

Terms used here: pose, node, window, a point's node, guess, motion model, placing, hand-off, NDT map, LM iteration, gyro bias, voxel. All basic terms: the guide's Fundamentals.

In one sentence The old loop was correct but did about 345 times more placement work than needed, and the work grew with the square of the number of windows; the fix does each placement once. On today's recordings the saving is about 7 seconds, because the scan-to-map optimization takes almost all of the time; on much longer recordings the old loop would have become a real cost.

1. Background: windows and placing a window

1.1 What a pose is

(The short definitions of pose, node and window are in the guide's Fundamentals; this section goes into the detail.) A pose is the sensor's position and orientation at one moment, in the world frame: x, y, z in metres and three angles om, fi, ka (roll, pitch, yaw, Tait-Bryan). In the code it is a 4 × 4 Eigen::Affine3d: a rotation R and a translation t, so that a point p given in the sensor's frame lies at R p + t in the world. The optimizer works with the six numbers (x, y, z, om, fi, ka) per pose.

A node is one pose with its timestamp: one per IMU sample. A window is a run of consecutive nodes, threshold_nr_poses of them (360 in l2-vertical.toml, about 0.4 s at the L2's IMU rate; 180 in livox-vertical.toml, 0.36 s).

1.2 Windows

A run cuts the recording into windows (see docs/PIPELINE.md). Each window is a short trajectory: a list of poses (Window::poses), one node every few milliseconds. On raw data/44 there are 690 windows of 360 nodes (248,400 nodes in all).

Before the odometry, each window's poses come from the IMU alone. The IMU data is one time-ordered stream and the windows are consecutive pieces of it, so their orientations join up: the AHRS filter runs over all samples in order. Their positions don't exist yet: the IMU trajectory holds orientations only, and every node sits at (0, 0, 0).

The window loop optimize_windows (src/application/run_odometry.cpp) processes the windows in order, and the optimization moves each window: it gives it positions, and it corrects its orientation, which drifts away from the IMU's. The next window must continue from that optimized end, not from where the IMU put it. Moving a window so that it starts at a given pose while keeping its shape (the IMU's motion from node to node) is placing it:

// src/domain/window_steps.cpp
void place_window_after(Window &window, const Eigen::Affine3d &start)
{
    Eigen::Affine3d m_last = start;
    auto tmp = window.poses;                         // copy of all 360 poses
    window.poses[0] = m_last;
    for (int k = 1; k < tmp.size(); k++)
    {
        Eigen::Affine3d m_update = tmp[k - 1].inverse() * tmp[k];   // relative pose k-1 → k
        m_last = m_last * m_update;
        window.poses[k] = m_last;
    }
}

One placement costs, per node, an inverse and two 4×4 matrix products, plus a copy of the window's pose vector (360 × 128 bytes ≈ 46 KB).

1.3 How a window's trajectory is computed, step by step

The placement above is one step of a longer chain. From the recording to the final trajectory:

  1. Orientation from the IMU (calculate_trajectory, src/application/lidar_odometry.cpp). The Fusion AHRS filter turns the gyro and accelerometer samples into an orientation per IMU sample. This trajectory has orientations only: every position is zero. The gyro bias is estimated and removed here first.
  2. Cutting into windows (compute_step_1, same file). After the first threshold_initial_points points (they seed the map), every threshold_nr_poses nodes become a window: poses and motion_model_poses both start as the IMU's orientations, plus each node's timestamp, IMU angles and raw accelerometer reading. A window with 1000 points or fewer is dropped. imu_motion_from_previous keeps the IMU's motion from the previous window's last node to this window's first.
  3. The first window is placed at the map's origin (place_window_after(windows[0], m_g)), and the map is seeded from the initial points.
  4. The guess of each later window (predict_window_poses, src/domain/window_steps.cpp). The window is chained onto the previous window's optimized last node, keeping the IMU's shape (the orientation increments, as in place_window_after). Its positions then come from one of:
    • the accelerometer, integrated from the previous window's final velocity (use_imu_translation_prediction; with imu_always_on it is integrated again from the start-velocity prior by integrate_window_translations);
    • no motion, when the window is detected at rest;
    • otherwise the previous window's velocity carried forward (or, without timestamps, the previous windows' mean step).
    The gyro-bias estimate carried from the previous window is also removed here (apply_gyro_bias_prior). The result is copied to motion_model_poses: it is what the IMU says the window looks like, and the motion-model terms of the optimization pull towards its shape.
  5. The optimization (run_lm_iterations → optimize_lidar_odometry). Up to nr_iter Levenberg-Marquardt iterations move all six numbers of every node at once, so that the window's LiDAR points fit the NDT map while the motion stays close to the IMU's: the gyro's rotation between nodes, the accelerometer's change of velocity, the velocity carried from the previous window. The first node is held fixed (the origin fix); the window can only change how it continues from there. What each of these terms contributes is shown by the per-term table (first reading).
  6. Hand-off. The window's last few nodes are re-propagated from the IMU with the bias estimated in this window (repropagate_window_tail), and the next window is placed after its new last node (place_window_after, section 2 is about this step). The estimated gyro bias, end velocity and acceleration offset become the next window's priors.
  7. After the odometry, loop closure and the consistency pass (when on) move the windows' poses again; the positions written to the output are the poses after these.

1.4 How the points' positions are computed

A LiDAR point is stored as it was measured: its coordinates in the sensor's frame at its own time (already shifted by the lever arm to the IMU), its timestamp and its intensity. It never gets a world position of its own; it is placed with a pose each time it is needed.

  1. Which node a point belongs to (compute_step_1). Each point is given to the window whose time range contains it, and within the window to the last node before its timestamp, if that node is at most 10 ms away (Point3Di::index_pose); otherwise it is dropped. The window's points are stored twice: all of them (WindowOriginal), and voxel-thinned with decimation (WindowIntermediate), which is what the optimization uses.
  2. Placing a point. With its node's pose, a point's world position is 
    world = poses[p.index_pose] * p.point          // R p + t of its node
    So a point moves exactly as its node moves: an error of the node's position moves the point by the same amount, and an error of the node's orientation moves it by the angle times its range (0.1° at 20 m is 3.5 cm).
  3. During the optimization every thinned point is placed this way with the current guess of its node, looked up in the NDT map, and pulls its node towards its cell.
  4. Into the map. When a window is done, its thinned points, placed with the window's final poses, are added to the NDT map (add_window_to_map → update_rgd); the next window is matched against them. A point placed with a wrong pose therefore stays in the map as a wrong wall for the windows after it.
  5. Into the output (save_result, points_to_vector). The windows are joined into chunks; each chunk's original points are placed with the final poses and written relative to the chunk's first pose (scan_lio_<i>.laz, with that pose in the session files), and once more in world coordinates into scan_lio_merged.laz. The trajectory CSVs hold each chunk's poses relative to its first node.
Why window placement matters for the map Everything a run outputs is "points placed with poses". The odometry decides the poses window by window, and each window starts where the previous one ended; a window that ends a few millimetres off hands that offset to every later window, until loop closure or consistency corrects it.

2. The old code

At the end of each window i, after its optimization, the loop placed every later window again:

// every later window continues from the new end of this one
for (int j = i + 1; j < windows.size(); j++)
    place_window_after(windows[j], windows[j - 1].poses[windows[j - 1].poses.size() - 1]);

After window 0 it placed windows 1–689 (689 placements), after window 1 windows 2–689 (688), and so on. In total:

QuantityFormulaOn 44 (n = 690, m = 360)
Window placementsn(n−1)/2237,705
Node updates (inverse + 2 products each)m · n(n−1)/2≈ 85.6 million
Pose data copied (the tmp vector)46 KB · n(n−1)/2≈ 11 GB
Needed placementsn − 1689

3. What was wrong with it

The results were correct: every window was processed starting from the right place. Three things were wrong with how it got there.

3.1 Almost all of the work was thrown away

A placement of window j only matters if something reads window j's absolute poses before the next placement overwrites them. Going through every step of the loop:

Step (before window i is optimized)What it reads
estimate_previous_velocitythe end of window i − 1 (already final) and only the timestamps of window i
predict_window_posesplaces window i itself from the end of i − 1, using only its relative poses
apply_gyro_bias_prior, is_turn_window, accelerometer termwindow i as it is at that moment
Optimization, map update, logswindow i only
GUI live previewonly windows already reported done

Nothing reads window j > i + 1 before its own turn, and by then it has been placed again after window j − 1. So of the 689 placements after window 0, only the one of window 1 was ever used; the other 688 were overwritten before anyone looked at them. That is 237,016 wasted placements out of 237,705, about 99.7 %.

3.2 The cost grew with the square of the recording

The waste is not a constant factor. The number of placements is n(n−1)/2, so a recording twice as long does four times the placement work, while everything else in the loop (the optimization, the map update) only doubles:

RecordingWindowsOld placementsOld placement time (est.)New placement time (est.)
44 (today)690237,7056.7 s (0.4 % of 27 min)0.02 s
3× as long2,000≈ 2.0 million≈ 56 s (1.2 % of 80 min)0.05 s
7× as long5,000≈ 12.5 million≈ 6 min (3 % of 3.3 h)0.13 s
29× as long20,000≈ 200 million≈ 94 min (12 % of 13 h)0.5 s

Times scaled from the benchmark in section 5 (old ∝ n², new ∝ n), for windows of 360 nodes. A whole run takes about 2.4 s per window, so 44 needs about 27 minutes.

3.3 It added rounding error that meant nothing

Each placement rebuilds the window from its own relative poses, tmp[k − 1].inverse() * tmp[k]. That is exact in theory, but in floating point each rebuild rounds a little. Window j was rebuilt j times, so window 689 went through 689 rebuilds before it was processed, each adding a little rounding noise. The benchmark measures how far the repeated placement drifts from a single one: at most 1.75e-8 (in metres for the translations) after 689 rebuilds on the synthetic windows. Tiny, but it is noise with no meaning, and it made the results depend on how many windows came before.

4. The fix

Only the next window is placed after each window:

-            // every later window continues from the new end of this one
-            for (int j = i + 1; j < windows.size(); j++)
-                place_window_after(windows[j], windows[j - 1].poses[windows[j - 1].poses.size() - 1]);
+            // the next window continues from the new end of this one; the windows after it are placed in their own turn,
+            // since no step reads a window's placement before the window before it is done
+            if (i + 1 < windows.size())
+                place_window_after(windows[i + 1], windows[i].poses[windows[i].poses.size() - 1]);

Each window is still placed after the optimized end of its predecessor before it is processed. That matters when the initial guess doesn't place it itself: with use_motion_from_previous_step = false, and for window 1 when the velocity prior is off. Simply deleting the loop would have been a real behaviour change, so it was not done.

4.1 The one place where the later windows did matter: a failed run

When the NaN check stops a run at window i, optimize_windows returns false, but the run is still post-processed and saved. With the old code, the windows after i happened to be chained from the earlier placements, so the saved trajectory had no jump. Without the full loop they would lie at their IMU-only positions. So the failure path now places all remaining windows once:

if (!add_window_distance(windows[i], poses_before_optimization, carry, ts_failure, logger))
{
    // the run stops here but is still saved: the remaining windows continue from this one's restored end
    place_windows_after(windows, i + 1);
    return false;
}

place_windows_after(windows, first) is a new helper in src/domain/window_steps.cpp. It places windows[first], windows[first + 1], … in order, each after its predecessor's end: n − first placements, once. It has a unit test (tests/window_steps_test.cpp) that checks the chaining, the kept relative poses, that earlier windows don't move, and that one call matches the old repeated placement within 1e-9.

5. How much faster

5.1 The placement work alone (benchmark)

A small benchmark (bench_chain.cpp, compiled with the same /O2 /fp:fast flags as the Release build) runs both loops on 690 synthetic windows of 360 nodes, the size of 44, using a copy of place_window_after:

LoopPlacementsTime
Old: all later windows after every window237,7056.5–6.8 s (3 runs)
New: only the next window6890.018 s
Saved≈ 6.7 s (about 370× less)

5.2 The whole run

Run (fast Release build)Odometry time, masterOdometry time, with the fix
44_short (70 windows)165 s today (155–218 s over earlier runs)163 s, 164 s
44 (690 windows)1651 s (earlier: 1508–1858 s)1567 s
Why the whole run barely changes The odometry spends about 2.4 s per window in the scan-to-map optimization (up to 100 Levenberg–Marquardt iterations over tens of thousands of points). The placement work was about 6.7 s over the whole run, against about 1,650 s. Run times of the same code vary by more than 10 % (other load on the machine, turbo clocks), which is far more than the saving. So the fix is real but cannot be seen in a single run time on 44: the full run with the fix took 84 s less than master's run of the same day, but only about 7 s of that come from the fix; the rest is run-to-run variation.
Where the fix does matter
  • Longer recordings: the old cost grows with n², so it would have cost about 3 % of a 5,000-window run and 12 % of a 20,000-window run (see the table in 3.2), and more from there on.
  • No meaningless rounding: each window is rebuilt once, not once per earlier window.
  • A clearer loop: the code now says what it needs, the next window's start, and a failed run is handled explicitly instead of by accident.
