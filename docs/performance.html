Performance: how the full recording got 2.2 times faster

Between 2026-10-05 and 2026-10-08 the processing of a full reference recording (about 5 minutes of data, 690 windows, 16.5 million points) went from 33 to 10 minutes, and its odometry from 26 to 8 minutes. This page shows what was measured, what each step changed, and what is left.

Terms used here: window, node, NDT map, LM iteration, term, loop edge, consistency pass. All basic terms: the guide's Fundamentals.

The six steps

StepOdometryWhole runWhat it did
Before (measured with log_stage_timing)1578.5 s1990 sOne core; the profile below.
Deterministic multithreading1059.6 s1467 sThe NDT point terms of a window's trajectory nodes run in parallel, each node's points still summed in their original order, so the result is the same bits as the single-threaded one. The NDT loops: 737 s → 180 s.
Banded normal matrix688.7 s1137 sThe dense 2166×2166 normal matrix (37 MB), zeroed and freed in every one of 69,000 iterations, is stored by band. Setup 4.1 → 0.17 ms per iteration; freeing it, 118 s → 4 s in total.
Fixed Cholesky pattern, /fp:precise509.8 s907 sThe symbolic analysis of the two sparse Cholesky solves is done 57 + 58 times in 138,000 solves instead of every time. One floating-point mode everywhere, at no speed cost.
Faster consistency516.7 s647 sThe normal equations of the consistency passes (10) are accumulated directly into a banded matrix instead of sparse products; the points and the Cholesky analysis are kept between passes; the 1M-point chunks are built in parallel and merged in order. Consistency: 363.6 → 44.7 s.
Stored NDT cell inverses490.5 s622 sThe inverse covariance of every NDT cell (and its usable flag) is stored once when the map is updated, instead of being inverted again by every point in every iteration; the node pose is converted once per node instead of once per point. The result is bit-identical.
Reprocessing from an odometry snapshot2026-10-11for loop-closure experiments: 178 s on the full reference recording instead of 1338 s for a full run (18 s instead of 179 s on a 30-second cut of it); bit-identical

Disk input and output is not a bottleneck inside the odometry: reading a window's points takes about 1 ms.

Did the results change?

Multithreading and the banded matrix did not change a single bit on the 30-second test recording, and the fixed pattern moved it by at most 1e-10 m. The floating-point mode did change the numbers, by more than expected:

/fp:fast → /fp:precise On the 30-second test recording the two baselines differ by up to 2 cm in position. On the full recording the calculated route is 215.46 m long instead of 216.06 m, and some per-window gyro-bias estimates differ by up to 0.19 °/s. The quality metrics of tools/eval_odometry.py are equal or slightly better with precise (window yaw difference 1.37 → 1.33 °, spikes above 3 °: 6 → 4, final yaw −126.4 → −126.0 ° against the gyro's −136.9 → −136.8 °). Without ground truth neither mode can be called closer to the truth. The switch was made because /fp:fast bought only 0–2 % speed while making the result depend on how the compiler ordered sums, which needed a second build and a tolerance rule for every check. The old baselines are kept as dated folders.

What is left

The whole run of 622 s now consists of (approximately):

StageTimeShare
Odometry490 s79 %
Consistency45 s7 %
Loop closure54 s9 %
Saving the result19 s3 %
Loading and preparing the windows14 s2 %

Four fifths of the run are now the odometry: the NDT point loops, the motion-model terms and the matrix assembly, plus the two Cholesky solves, which are mostly numeric work. Loop closure is the next sizeable piece.

Details, the method and every number: PERFORMANCE.md in the repository. Times are for the reference recordings with the Release build; the machine has 16 logical cores.
