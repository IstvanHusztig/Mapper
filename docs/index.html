dMapper guide

dMapper turns a LiDAR + IMU recording into a trajectory and a point cloud. Five ways into this guide: the basic terms (pose, node, window, term …), explained once and linked from every page; how it works, step by step from the recorder's LAZ file to the final map, with the pages that explain each step in depth; the settings, every parameter of the settings file; the internals, how the code is laid out and how the work on it is organised; and all documents, every page of docs/ by what it is for.

What the odometry does with the points it reads

The program is a LiDAR-inertial odometry. The IMU gives a fast but drifting estimate of how the sensor rotated. The LiDAR sees the surroundings, which do not move. The program cuts the recording into short windows of about 0.4 s. Each window's trajectory is adjusted until its points line up with the map built from all previous windows, without contradicting the IMU more than its noise allows. Every point keeps its own timestamp and gets its own pose, so the motion during a sweep is compensated (deskewed).

Values on this pageThe values shown are those of settings/l2-vertical.toml. Sensor-specific values (IMU noise, lever arm, range, window length in IMU samples) differ per sensor; see Supported sensors.

Fundamentals: the basic terms

The words below are used on every page of this guide with exactly this meaning. Other pages link here the first time they use one, so each term is explained once. Each entry ends with where it is explained in depth.

Frames and samples

Sensor frame
The coordinates a point is measured in: relative to the scanner at the moment of the measurement, in metres, Z up, NWU (x forward, y left, z up). Every point is shifted by the lever arm once on loading, so its sensor frame is the IMU's.
World frame
The fixed frame the map and the trajectory are in. Its origin is where the first window starts; its z axis is up (gravity), its heading is the AHRS heading (the filter starts at the beginning of the recording).
Lever arm
The offset from the LiDAR's origin to the IMU's (lidar_imu_lever_arm_*), applied as a translation only; the points must already be in the IMU's axes. → step 1
Timestamp
Every point and every IMU sample carries one, in nanoseconds on one shared clock. The streams must agree within a few milliseconds; a lagging IMU is corrected before processing. → Inputs, Best practices
IMU sample
One reading of the gyro (rotation rate, three axes) and the accelerometer (specific force, three axes) with its timestamp: about every 1.1 ms on the Unitree L2 (about 900 Hz), every 2 ms on the Livox Mid-360S (500 Hz).
AHRS, Fusion AHRS, AHRS orientation
An AHRS (attitude and heading reference system) turns the IMU samples into an orientation. dMapper uses Fusion (the open-source AHRS library by x-io Technologies, vendored in 3rdparty/Fusion), a Madgwick-type complementary filter, in its 6-axis form (gyro and accelerometer, no magnetometer):
  • it integrates the gyro from sample to sample, which gives every turn quickly and accurately, but lets errors grow: a gyro bias of 0.1 °/s is 6° of heading per minute;
  • it pulls roll and pitch towards gravity, the direction the accelerometer measures, with the strength ahrs_gain (0.05 in both sensor settings). A small gain trusts the gyro more, so walking accelerations barely tilt the estimate, but a tilt error is corrected only slowly. For the first 3 s Fusion starts from a gain of 10 and ramps it down to ahrs_gain, so the first orientation is levelled quickly;
  • heading (yaw) has no reference without a magnetometer: it is whatever the gyro integrates to, starting from the beginning of the recording, and drifts with the gyro bias. Fixing it is the LiDAR's job in the optimization;
  • Fusion's acceleration rejection (ignoring the accelerometer while it measures more than gravity) is off; the fusionConvention* settings choose the axes (NWU in both sensor settings).
The result, the AHRS orientation, is one rotation per IMU sample: the orientation of every node before the odometry, and the gyro's shape of each window's guess. The pipeline uses it through the OrientationEstimator port (src/application/service_ports.h); the adapter FusionOrientationEstimator (src/infrastructure/fusion_orientation_estimator.cpp) only wraps Fusion, and the bias removal, the start-up bias and the time steps are in calculate_trajectory. → step 2, [madgwick_filter]

Poses and trajectory

Pose
The sensor's position and orientation at one moment, in the world frame: x, y, z in metres and three angles ω, φ, κ (om, fi, ka: roll, pitch, yaw, Tait-Bryan). As a matrix it is a rotation R and a translation t, so a point p of the sensor frame lies at R p + t in the world. The optimizer works with the six numbers. → Poses and window chaining, section 1.1
Node (trajectory node)
One pose with its timestamp. There is one node per IMU sample, so nodes are about 1–2 ms apart. Before the odometry a node has the AHRS orientation and position (0, 0, 0); the odometry gives it its position and corrects its orientation.
Trajectory
All nodes in time order: the path of the sensor. The output's trajectory_lio_N.csv holds one node per line.
A point's node (index_pose)
Each point is attached to the last node before its timestamp, if that node is at most 10 ms earlier (otherwise the point is dropped). Its world position is always pose(node) × point, so a point moves exactly as its node moves: a 0.1° error of the node moves a point 20 m away by 3.5 cm. → step 3, window chaining, section 1.4
Motion compensation (deskewing)
A LiDAR sweep takes time while the scanner moves. Because every point is placed with the pose of its own node, the points of one sweep are placed with the motion during the sweep, not with one pose for all.

Windows

Window
A run of consecutive nodes, threshold_nr_poses of them (360 ≈ 0.4 s on the L2, 180 ≈ 0.36 s on the Mid-360S), with the points recorded in that time. The odometry optimizes one window at a time, in order; recording 44 has 690 windows. → step 3, How a run works
Guess (initial guess)
A window's poses before its optimization: chained onto the previous window's optimized end, rotations from the IMU minus the gyro bias, positions from the accelerometer (or a constant velocity). → step 5
Motion model
A copy of the guess kept as the IMU's "measurement" of the window's shape: the optimization may move the window, but the motion from node to node is pulled towards the motion model's.
Placing (chaining) a window
Moving a whole window so that it starts at a given pose while keeping its shape (the motion from node to node). Each window is placed after the previous window's optimized last node. → window chaining, section 1
Hand-off
What passes from one window to the next: the end pose (after the last handoff_tail_nodes nodes are recomputed from the IMU, because they have almost no points), and the estimates of the gyro bias, the velocity and the acceleration offset, which become the next window's priors. → step 7
Chunk
A group of 51 windows written as one scan_lio_N.laz on export, relative to its first pose. → step 9

The map

Voxel
A cube of a regular 3D grid laid over space, the 3D counterpart of a pixel: every point falls into exactly one voxel, found from its coordinates divided by the voxel size. A voxel holds whatever the grid keeps for its points. In dMapper that is one point (decimation), or a mean and covariance (an NDT cell), or one coloured point in the GUI's live preview (0.10 m). The size sets the detail: a smaller voxel keeps more detail and more points.
Decimation (voxel thinning)
Keeping only the first point in each voxel of size decimation (0.03 m in both sensor settings). The optimization and the map use the thinned points; the export uses all of them.
NDT map, grid, cell
The map the windows are matched against (Normal Distributions Transform). Space is divided into voxels, the cells, of two grids: 0.15 m (indoor) and 0.4 m (outdoor). Each cell stores the mean and covariance of the points in it, a small Gaussian that describes the local surface, and with at least 3 points and a clear surface direction a normal facing the sensor. A window's points, placed with its optimized poses, are added after each window. → step 4, step 8

The optimization

Unknowns
The numbers the optimization of a window changes: six per node (6 × 360), three for the gyro bias, and with imu_always_on nine more (the start and end velocity and the acceleration offset).
Term
One kind of measurement the window must agree with: the points against the NDT map (one term per grid), the motion model between nodes, the velocity continuity, the accelerometer, the priors and the origin fix. Each adds its equations to one least-squares problem. → step 6
Residual
How far one measurement is from what the current poses predict: a point's distance from its cell's Gaussian, a node-to-node motion's difference from the IMU's, and so on.
Sigma, weight, information
A sigma is the expected size of a residual: its noise. A residual is weighted by 1 / sigma², so a small sigma is a strong term. The weights added up over a direction are the information about that direction: how firmly the measurements fix it. Every weight of a window comes from its noise model, built once before the window's first iteration; each run logs its noise budget, and log_window_noise logs every window's sigmas.
Cost
The sum of all weighted residuals squared. The optimization looks for the poses with the smallest cost.
Prior
A term that holds an unknown near a value known before the window, within a sigma: the gyro bias near the previous window's estimate, the start velocity near the previous window's end velocity.
Origin fix
The window's first node is held at the previous window's end within a very small sigma (fix_origin, 1e-6); the window can only change how it continues from there.
Levenberg–Marquardt iteration, damping
One iteration linearizes all terms at the current poses, solves the least-squares system, and moves all unknowns by the step. The damping shortens the steps: it starts at lm_factor_initial and grows tenfold every 10 iterations, and also after each rejected step. A window runs up to nr_iter iterations, or stops early at the time limit real_time_threshold_seconds. → step 6

IMU states

Gyro bias
The gyro's offset: the rotation rate it reports when not turning. Uncorrected it turns the heading steadily. Each window estimates it (three numbers) and hands it on, within a sigma that grows by the bias random walk. → step 7, [gyro_bias_estimation]
Velocity (start and end)
With imu_always_on, a window's velocity at its first and last node are unknowns. The end velocity is handed to the next window as the prior of its start velocity. → [imu_translation]
Acceleration offset
A slowly changing error of the accelerometer (three numbers), estimated per window and carried like the gyro bias, so it isn't read as motion.

Readings of a run

Degeneracy, information ratio
A window is degenerate when its points can't fix every direction of motion, such as along a straight corridor. The information ratio is the smallest over the largest eigenvalue of the LiDAR's translation information in the window: 0 = blind in one direction, 1 = equally fixed everywhere. → Degeneracy information
Bend (heading, roll, pitch)
How far the optimization turned a window's last node away from its guess, which came from the gyro: the heading bend is the turn about the vertical, roll and pitch bends about the horizontal axes. A large bend means the LiDAR overruled the gyro.
Velocity chi²
The squared distance of a window's start velocity from its prior, measured with the prior's covariance (three residuals). Around 3 or below when the velocity agrees with the previous window within its noise.
Window verdict, flags
After each window four flags are judged: bent (any bend above 3°), bent severely (above 10°), fast (above 2.5 m/s) and bias high (gyro bias above 0.5 °/s). Each is CLEAR, TRIGGER or NOT MEASURED (the window doesn't have the reading). The run's window verdict summary counts them. Investigation triggers, not a statement about the map. → [lidar_odometry_debug_info]
Per-term table (hold, pull, remaining step)
For each window and each term: how strongly the term alone holds four motions of the window (shift, stretch, curve, turn) along travel, sideways and vertical (the hold, a sigma), and where the term alone would move it (the pull). The remaining step is the pull of all terms together. → The per-term table

After the odometry

Segment
A group of loop_closure_segment_windows windows (6 ≈ 2.4 s) that loop closure moves as one rigid piece.
Loop closure, loop edge
When the path comes back to a place already scanned, the later segment is registered against the earlier one; an accepted registration becomes a loop edge, the measured offset between the two segments. → Loop closure (after step 8), Loop closure research
Pose graph
The segments' poses as unknowns, joined by odometry edges (consecutive segments) and loop edges, optimized together; the correction is then spread over every node.
Consistency pass
An optional optimization of the whole trajectory at once against one map of the whole recording, after loop closure. → Consistency pass (after step 8)

Runs and checks

Settings file
The TOML file of a run (settings/l2-vertical.toml, settings/livox-vertical.toml); the output folder keeps a copy as dMapper_params_*.toml. → Parameter reference
Capture and replay
A run can save the window loop's state before a stretch and that stretch's windows (a capture); --replay then runs only that stretch again in seconds, bit for bit with the same settings. A snapshot saves the whole odometry result, so loop closure and consistency can be rerun alone. → [lidar_odometry_debug_info]
Baseline, manifest, bit-identical
A refactor must not change a single bit of the results. A manifest lists the checksums of a reference result (tools/baseline/*.manifest.json), and tools/compare_baseline.py compares a new result with it file by file. → tools/README.md

The pipeline

Steps 5 to 8 repeat for every window (dashed arrow). The sections below follow one point through all of them.

  1. Loading and filtering the points

    load_data / load_point_cloud · src/application/lidar_odometry.cpp, src/infrastructure/recording_folder_source.cpp

    Each point is read with its position in the sensor frame, its intensity and its timestamp. Then:

    • Each point is shifted by the LiDAR→IMU lever arm (translation only), so that points and IMU share one origin. The points must already be in the IMU axes (NWU: x forward, y left, z up); no rotation is applied.
    • Points with timestamp 0 are dropped.
    • Points whose horizontal distance √(x²+y²) in the sensor frame is below filter_threshold_xy_inner (the handle, your hand, the housing) or above filter_threshold_xy_outer are dropped.
    • The points of each file are sorted by time. The IMU CSVs are read, merged and sorted by time.
    filter_threshold_xy_innerfilter_threshold_xy_outerlidar_imu_lever_arm_*

  2. An orientation for every IMU sample

    calculate_trajectory · src/application/lidar_odometry.cpp

    A Madgwick-type filter (Fusion AHRS, 6-axis, no magnetometer) integrates the gyro, and uses the accelerometer's gravity direction to correct roll and pitch. Heading (yaw) has no absolute reference, so it drifts with the gyro bias. That is what the LiDAR optimization and the bias estimation fix later. The accelerometer's pull has the constant strength ahrs_gain for the whole recording. (Until 2026-11-16 the code tried to switch it off while |a| was outside 0.9–1.1 g; Fusion ramps its gain down from 10 over the first 3 s and then keeps its own copy, so that switch never took effect and was removed.)

    If use_remove_imu_bias_from_first_stationary_scan is on, the median gyro value of the first startup_gyro_bias_nr_samples samples (1000) is subtracted as bias, but only if the total gyro variance there is below startup_gyro_bias_max_variance_deg2_s2 (5 (°/s)²). Handheld recordings usually fail that check ("Excessive movement detected") and continue with zero bias.

    Result: a trajectory map timestamp → rotation with one entry per IMU sample (about 1.1 ms apart). These are the trajectory nodes. Their positions are still zero at this stage.

    ahrs_gainfusionConvention*use_remove_imu_bias_from_first_stationary_scanstartup_gyro_bias_*

  3. Windows and a pose for every point

    compute_step_1 · src/application/lidar_odometry.cpp
    • The first threshold_initial_points points are set aside to build the initial map (step 4). Nodes before the time of the last of these points are skipped.
    • The remaining nodes are cut into windows of threshold_nr_poses consecutive nodes (360 ≈ 0.4 s at about 900 Hz; counted in IMU samples, so set per sensor, see Supported sensors). A leftover shorter than a full window is dropped.
    • Every point in the window's time span is attached to the node just before its timestamp (its index_pose), but only if that node is at most 10 ms earlier. Otherwise the point is dropped. Windows with ≤ 1000 points are dropped.
    • Two copies are cached on disk (<input>/cache): all points (for export) and a voxel-decimated copy that keeps the first point per decimation-sized cube (used in the optimization).

    From here on, a point is always used as pose(index_pose) × point. Correcting a node's pose moves exactly the points recorded in that ~1 ms, and this is how motion during the scan is compensated.

  4. The initial map

    optimize_windows (start) · src/application/run_odometry.cpp

    The set-aside initial points are transformed with the first pose only (no per-point motion compensation) and inserted into two NDT grids. Space is divided into cubes (0.15 m "indoor" and 0.4 m "outdoor" grid), and each cube stores the mean and covariance of the points in it, i.e. a small Gaussian that describes the local surface. A cube with 3 or more points also gets a normal vector facing the sensor.

    Because this map is not motion-compensated, stand still for the first second or two if you can. The first window is registered against this map, so its misfit is not allowed to affect the gyro bias estimate.

    in_out_params_indoor.resolution_*in_out_params_outdoor.resolution_*threshold_initial_points

  5. Initial guess for the next window

    optimize_windows · src/application/run_odometry.cpp
    • The window's first node is placed exactly on the previous window's last node.
    • Rotations follow the IMU's relative rotations between nodes, minus the gyro bias estimated so far (bias × Δt per step).
    • Positions, with imu_always_on (on in the shipped settings): the accelerometer integrated from the start velocity carried over from the previous window, with that window's gravity and acceleration offset (integrate_window_translations). A window at rest keeps a motionless guess. Without it: a constant velocity, the velocity over the last prior_velocity_span_nr_samples nodes of the previous window (use_motion_from_previous_step).

    This guess is also stored as the motion model: the IMU "measurement" the optimizer compares against.

    In depthPoses, windows and window chaining (section 1.3: how each window's guess is chained and placed)

  6. Window optimization

    optimize_lidar_odometry · src/domain/scan_to_map.cpp

    The unknowns are the 6 pose parameters (x, y, z, ω, φ, κ) of every node of the window, plus 3 gyro-bias values: 6 × 360 + 3 = 2163 numbers. With imu_always_on there are 9 more: the acceleration offset and the velocity at the window's start and end. Each Levenberg–Marquardt iteration builds one least-squares system from these terms:

    • Point to map (NDT, fine grid): every decimated point with 3-D distance between min_distance_lidar and max_distance_lidar is transformed with its node's pose and looked up in the 0.15 m grid. Its distance to that cube's Gaussian, weighted by the inverse covariance, is minimized. Points hitting a cube whose normal faces away from the sensor, or whose covariance is degenerate, are skipped. Two optional settings shape this term (both off for the L2, on in settings/livox-vertical.toml): ndt_huber_cutoff gives a point farther than that many standard deviations from its cube a constant pull instead of one that grows with the distance (Huber kernel), so a few wrongly matched points can't drag the window; ndt_information_scale multiplies the weight of all point terms, so the IMU terms count more against them.
    • Point to map (NDT, coarse grid): the same with the 0.4 m grid, for points between min_distance_lidar_outdoor_grid and max_distance_lidar.
    • IMU motion model: between consecutive nodes, the relative pose should match the guess. Translation is held tightly (*_x/y/z_1_sigma_m). Rotation may deviate by max(k × ARW × √Δt, floor) per axis, i.e. about what the gyro can drift in that Δt (time-scaled rotation prior). The gyro bias enters here: the IMU step is corrected by −bias × Δt. While the accelerometer term is active, imu_position_information_scale scales the weight of the translation part (1 = unchanged; 0.1 in the Livox settings), so the accelerometer and the points decide the positions more.
    • Velocity continuity: the velocity may only change as much as acc_1_sigma_mps2 allows, including across the boundary to the previous window. The previous window's final velocity is measured over its last prior_velocity_span_nr_samples nodes; if it is faster than max_prior_velocity_mps, it is not used, and the window starts from 0 m/s without that link.
    • Accelerometer, always on (imu_always_on, on in the shipped settings): in every window from the second on, the change of velocity between nodes about 10 ms apart must match R · f − g minus the acceleration offset e. The term also moves the node rotations, so a tilt that leaks gravity into the acceleration is corrected in the attitude, not smeared over hundreds of positions. Each term is weighted by the sensor's noise: σ² = imu_accel_noise_density_mps2_sqrt_hz² / τ + imu_accel_floor_sigma_mps2² over its span τ. The second part is the vibration floor: walking shakes the handheld scanner far more than the noise measured at rest, and the floor keeps those shakes from being read as motion. The start and end velocities are unknowns with priors carried from window to window, like the gyro bias. A window at rest gets a zero-velocity measurement. A term whose span is stretched by an IMU gap is dropped. In a blind passage the window keeps the speed the accelerometer measures, instead of stalling when the LiDAR can't see it move (see [imu_translation]).
    • Fixed start: node 0 is locked to the previous window's end (fix_origin sigmas, 1e-6).
    • Bias prior: the bias stays near the previous window's estimate, within its uncertainty grown by the bias random walk.

    The system is solved with a sparse Cholesky factorization. Up to nr_iter iterations run; the damping starts at lm_factor_initial and is multiplied by 10 every 10 iterations and after each rejected step (pose unknowns only). A window stops early when the sum of all parameter updates of one iteration falls below convergence_delta_threshold (default 1e-12, which is practically never reached, so all iterations run), or once it has run for longer than real_time_threshold_seconds. Only the band of the normal matrix that can hold values (neighbouring nodes and the bias unknowns) is converted to sparse form each iteration.

  7. Hand-off and gyro bias

    optimize_windows · src/application/run_odometry.cpp

    The last node of a window has no points, and the ones just before it have very few. Left free, they can spin by several degrees, and the next window would inherit that error permanently, which shows up as rotated "ghost" copies of walls. So after the optimization, the last handoff_tail_nodes nodes are recomputed from the last well-constrained node using the bias-corrected IMU rotation and the optimized velocity. The next window starts from that recomputed end.

    The window's bias estimate and its uncertainty become the prior for the next window, and they are printed and written to the results JSON.

  8. Map update

    optimize_windows · src/application/run_odometry.cpp

    The window's decimated points, now transformed with their optimized poses, are added to both NDT grids (the Gaussians are updated incrementally). The map therefore grows with the whole recording. Once the travelled distance exceeds sliding_window_trajectory_length_threshold, the map is rebuilt from the most recent half of the points, voxel-decimated with decimation, which bounds memory on long runs. With the default 200 m this happens rarely on handheld recordings.

    sliding_window_trajectory_length_threshold

  9. Export

    save_result · src/application/lidar_odometry.cpp

    All original points (not the decimated ones) are transformed with their own optimized node pose. Points whose sensor-frame distance is below threshould_output_filter are removed from the export. Windows are grouped into chunks of 51, and each chunk becomes one scan_lio_N.laz, expressed relative to the chunk's first pose, with that pose stored in the session files. The remaining windows form a final, shorter chunk, which is written if it has more than min_counter_concatenated_trajectory_nodes windows (default 0, so it is always written).

    With export_merged_laz = true all chunks are additionally written into one scan_lio_merged.laz in world coordinates.

Loop closure (after step 8, before the consistency pass)With use_loop_closure = true the run (command line and GUI alike) corrects the finished trajectory when you come back to a place you have already scanned (src/application/loop_closure.cpp):
  1. The windows are grouped into segments of loop_closure_segment_windows windows (6 ≈ 2.4 s), each with its points in world coordinates. With longer segments (12 windows ≈ 5 s) a turn of the path often lies inside one rigid segment, and the graph can twist an out-and-back passage by a few degrees.
  2. Revisit candidates: for every segment, the earlier segments with at least loop_closure_min_path_m walked in between, whose centre lies within min(loop_closure_search_radius_m, loop_closure_radius_per_path × that path) horizontally and loop_closure_max_vertical_offset_m vertically (so different floors are not confused), longest path first. The path counts a step only once the position moved 0.1 m, so standing still adds nothing; a dead end walked out and back qualifies however short the time, neighbouring segments and places seen from afar don't, and a near revisit does not take the place of a far one (the loop closure of a whole round). Up to loop_closure_candidates of them are registered, chosen to differ, in this order: the nearest one, the longest-path one, the nearest at least 3 segments away from the nearest, and the longest-path one at least 3 segments away from the longest-path one (a smaller limit keeps both kinds). Of the accepted registrations, up to loop_closure_edges_per_segment become loop edges: the best of the near ones and the best of the far ones by overlap after the refinement, both only if their earlier segments are at least 3 apart (otherwise the better one). An old parameter file with loop_closure_min_time_gap_s still loads; the key is ignored, since a minimum time between visits would never compare a passage walked out and back quickly.
  3. Registration: the later segment is aligned to the earlier one and its neighbours, first by a voxel-overlap search over yaw (±10°) and translation (±loop_closure_max_correction_m), then by point-to-distribution refinement. It is accepted only if at least loop_closure_min_fitness of its points overlap the earlier visit, the overlap did not get worse, and the correction stays within the search range and 15°.
  4. Pose graph: the segment poses are optimized with odometry edges between consecutive segments and the accepted loop edges, the first segment fixed. A step is kept only if it lowers the graph's error (damped otherwise). Every loop edge, on the same floor and between floors, is weighted by what its registration determines (its NDT normal matrix mapped into the edge, scaled so that the best-determined translation gets loop_closure_edge_sigma_m; see loop_closure_cross_floor_max_vertical_m below); an edge whose registration information is unusable keeps the fixed sigmas. A weak direction, such as along a corridor or the turn of a narrow passage, then pulls little, and the loop closure no longer invents turns the odometry didn't make. Then each loop edge is compared with the solution: of the edges that disagree by more than loop_closure_max_residual_m or loop_closure_max_residual_deg (in their weighted residual), the one whose removal lowers the error of the re-solved graph the most is a false match; it is dropped and the graph solved again, until all edges agree. One false edge would otherwise bend the trajectory by decimetres and leave a ghost wall. The result is applied only if it is finite and no segment moved further than loop_closure_max_correction_m plus the largest accepted correction; otherwise it is discarded with a warning and the trajectory stays as it was.
  5. The correction of each segment is interpolated onto every trajectory node, so the trajectory bends smoothly instead of jumping.
The log lists every candidate with its overlap before/after and the correction, every dropped edge, and the residuals of the edges kept. Errors larger than the search range (for example a 20° heading failure) are rejected on purpose; they come from the odometry and have to be fixed there.
Optional: consistency pass (between steps 8 and 9)With use_consistency = true the run (command line and GUI alike) calls run_consistency after the odometry and loop closure, before the export. It re-optimizes the whole trajectory at once, num_constistency_iter times: every node is pulled towards a smooth trajectory (relative-pose prior between consecutive nodes), and points from all windows must agree with one NDT map built from the whole recording. This can remove residual misalignment between windows, such as a wall seen at the start and again at the end, but it is slow and it can also smear the trajectory if the smoothness prior is too strong. It uses one Gaussian per indoor-grid cube and a rotation smoothness of 0.1°, and ignores points closer than 1 m. (A second variant, Consistency2 with one Gaussian per cube and time segment, was removed on 2026-11-16: no sensor setting used it.) See Fixes and map sharpness for measured effects.

[imu_translation]

Best practices

Most of the map quality is decided while recording. The odometry can only correct what it can observe twice, so plan the walk so that every part of the building is seen again later.

Recording

  • Walk a loop on every floor. Come back to a place you have already scanned on the same floor (a room, a corridor junction, the stair landing) at least 30 s after the first visit, and pass within a few metres of where you walked before. Each such revisit lets loop closure pull that floor into line. A floor walked only once cannot be corrected: the heading errors on the way down and back up the stairs can cancel out and leave that floor rotated by a few degrees, with no loop to expose it.
  • Close the loop on the floor, not only through the stairs. A revisit on another floor is not matched (loop_closure_max_vertical_offset_m = 1.5 m), so each floor needs its own revisit.
  • Pause at feature-rich spots briefly before and after long featureless stretches (one-sided corridors, open halls), so the distance across them is anchored at both ends.
  • Hold still for 3–5 s at the start. The initial map is not motion-compensated (see Known limitations). With imu_always_on, a window at rest also pins the velocity and the accelerometer offset. Keep yourself out of the scanner's near field in the first second. Short stops later on help in the same way.
  • Take stairs steadily and look around at each landing; stairwells are where the odometry is weakest.

Processing

  • Use the Release build with the settings file of the sensor, from the command line or loaded in the GUI (Start → Load parameters); both run the same stages, including loop closure and the consistency pass, and give the same result.
  • The IMU and LiDAR timestamps must agree within a few milliseconds. If the IMU lags the LiDAR, measure the offset with tools/imu_time_offset.py and correct it with tools/restamp_imu.py before processing (see tools/README.md).
  • Check the result per floor: walls seen on different passes should overlap as one surface. If a room appears twice or a floor is rotated, see the tuning cheat sheet.

Consistency pass

use_consistency (on in the shipped settings) pulls every window towards one map of the whole recording after the odometry, which removes the small offsets left between windows and thins the walls, at the cost of one more pass. Its weak smoothness prior (0.1°) lets the trajectory roughen, which does not blur the map, because each node is re-fitted to the points. Set use_consistency to false when runtime matters more than map quality.

Known limitations

  • Initial map is not motion-compensated. The first ~60k points are placed with the first pose only.
  • A fragile window in a fast turn onto stairs. The scan-to-map match of one window can land about one step (0.3 m) off. Whether it does can depend on rounding: a /fp:precise and a /fp:fast build of the same code can decide differently, and from there the odometry runs away. Cause: a map cell's mean is the first point that fell into it, so a sub-millimetre pose difference gives new cells other means and the next window matches against a slightly different map; and a point that leaves the map costs nothing, so a window can slide away from the surfaces. A fix is planned as its own change.
  • IMU timestamps. A recorder that stamps the IMU samples on their arrival at the host stamps them in bursts and tens of milliseconds later than the LiDAR points; on such data the accelerometer makes results worse. Both streams must carry the sensor's own timestamps on one clock; a lagging IMU is corrected with tools/restamp_imu.py before processing.
  • Stairwells. Between floors, in the stretch where nothing mapped before is in view, the heading drifts by a few degrees (the gyro bias is known only to a few hundredths of a °/s), and a return between floors can fail by more than loop closure accepts. The cross-floor edges correct the drift, but their tilt is not fully reliable: the stairs of two floors are not exactly alike, so a registration can be precise and still off by about a degree, and storey heights can vary between runs by centimetres to decimetres.
  • NDT cell normals. By default a map cell's normal is fixed from its first 3 points and its mean is its first point; neither is updated later. Many normals are wrong (60 % on a synthetic corridor), which makes the degeneracy test noisy and costs about 1 mm in the scan-to-map fit. use_exact_ndt_bucket_statistics = true fixes the statistics, but it is off: with the current threshold it marked several times as many windows of a real recording as degenerate, and the map was less sharp. See Degeneracy information.
  • Loop closure only corrects revisits it can register (≥ 50% overlap, ≤ 6 m, ≤ 15°).
  • Loop closure also moves a correct trajectory. On the synthetic two-lap recording of the unit tests (tests/loop_closure_test.cpp) it halves a second-lap drift, but a trajectory that is already exact is moved by up to 3 cm and 0.1°: every revisit registers with a residual of 1–3 cm, and the pose graph trusts loop edges to 5 cm. With points only within 6 m it accepted a wrong registration and moved the trajectory by 1.5 m; the overlap threshold alone does not catch that.
  • The consistency pass also moves a correct trajectory, on the same synthetic recording (tests/consistency_test.cpp): by up to 6 mm (spread evenly, the noise of the NDT fit). It removes offsets between windows.

One window, in the code

The pipeline above in code terms: OdometryPipeline loads the recording and cuts it into windows (compute_step_1), then the window loop (process_windows, src/application/run_odometry.cpp) runs four steps for each window:

  1. prepare_window: load the window's points, make its guess from the previous window (predict_window_poses: chaining, the rest test, the translation guess), set the carried priors, and build the window's noise model (WindowNoiseModel): every weight of the window, computed once.
  2. solve_window: the Levenberg–Marquardt iterations (lm_solve, src/domain/lm_solver.cpp) over the window's problem (WindowProblem). Each iteration asks every term for its equations in a fixed order: the NDT point terms per grid (ndt_term), the motion edges, gyro-bias prior and velocity continuity (motion_model_terms), the accelerometer terms and the velocity and offset priors (accelerometer_term), the origin fix. The terms read their weights from the noise model and never compute them. The solver records why the iterations stopped.
  3. report_window: the log lines, the optional per-term table (log_window_terms) and noise line (log_window_noise), and the window verdict.
  4. finish_window: hand the gyro bias, velocity and offset to the next window, re-propagate the window's tail, place the next window, and add this window's points to the map.

After the loop: loop closure and the consistency pass (post_process), then the result files. Every run logs a noise budget line at the start and a window verdict summary at the end of the odometry.

How a change is checked

  • A refactor must not change a bit. python tools/step_checks.py builds, runs the unit tests, compares two guards (a characterization of single iterations and a loop guard, both as exact hexadecimal numbers), replays two captured stretches (44_short 20–40 s, Livox 3 100–130 s) window by window, compares the per-term table, and runs 44_short against its manifest (about 2 of the 7 minutes). "IDENTICAL" everywhere means the change changes no number.
  • Once per change, python tools/end_runs.py runs the full 44, Livox 3 and 44_short against their manifests (about 50 minutes, in the background); with --debug also the Debug build and its tests.
  • A stretch in seconds: a run with capture_windows_from_s / _to_s saves a stretch; python tools/run_replay.py <capture> <settings> runs only that stretch again, through a gate that waits until enough memory and a slot are free (a replay needs about three times its capture file).
  • A number that changes is judged on the run's log (the run check), on the map (the map check, and the user's own look at the clouds), and against the spread of small perturbations when one variant is claimed to beat another. Once accepted, the new manifests (and baseline folders) go into a commit of their own. See Fixes and map sharpness.

The main session (the orchestrator) owns what the regions share: the shared types and settings, the window loop's skeleton, capture and replay, the pipeline, the presentation layer, the docs. Who owns which file and function is one list, docs/regions/owners.toml; python tools/region_owners.py checks it, and with --diff lists what a branch touches outside its region. Several agents, one machine: the gate. Agents work side by side, and a replay costs memory (about three times its capture file: 0.2 GB for the 44_short capture, 1.6 GB and about 5 cores for the Livox 3 one) while a full run of a recording must not be slowed down (a window that runs past the time limit changes the result). So every replay and every full run goes through one gate, the script tools/run_replay.py (and tools/end_runs.py for full runs):

  • at most two replays run at once, and a replay starts only when its estimated memory plus a reserve is free ([gate] in tools/local_paths.toml);
  • a full run has the machine alone: replays wait until it ends, and it waits until they end;
  • a job waits before it starts and says what it waits for; a running job is never paused, because a pause frees no memory and a paused window would run past the time limit;
  • after each replay the script prints its wall time, CPU time and peak memory, and how many windows stopped at the time limit (above 0: the result depended on the machine's load, so the replay is run again).

The agents themselves are managed by the main session: it starts each agent with one question and a worktree, lets at most two editing agents work at once (one per standing worktree), runs the full runs and the snapshot runs an agent asks for, and decides what is merged. An agent cannot start other agents.

From a question to a merged change

  1. Question and capture. The main session states the question and captures the stretch.
  2. Triage. It reads the stretch's verdict lines, per-term table and noise lines, and names the region they point to.
  3. Region job. The region's agent works in a worktree of its own (a second checkout of the repository with its own build: C:/Repo/dMapper-worktrees/region-a or region-b) on a branch of its own. It changes only what its region owns, measures by replay, commits on its branch and hands the branch back with its numbers. It never touches the main checkout, never merges, pushes, starts a full run or changes the settings files. At most two agents work at once.
  4. Verification. The main session checks the branch against the ownership list; the verification agent runs the step checks in the agent's worktree, and for a change that moves numbers the replays before and after and the run and robustness checks.
  5. Review. The conclusion reviewer checks the finding.
  6. Merge or decision. A branch that changes no number the main session merges on its own judgment. A branch that changes a number is merged only after the user has seen its numbers (without a verdict) and, for anything that changes the map, looked at the before and after clouds. After each merge the step checks run on the main checkout again, because two branches merged one after the other were never tested together.
