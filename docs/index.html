What the odometry does with the points it reads

A reference for lidar_odometry_step_1: how every LiDAR point travels from the recorder's LAZ file to the final map, and what each parameter in settings/lidar-vertical.toml controls.

The program is a LiDAR-inertial odometry. The IMU gives a fast but drifting estimate of how the sensor rotated. The LiDAR sees the surroundings, which do not move. The program cuts the recording into short windows of about 0.4 s. Each window's trajectory is adjusted until its points line up with the map built from all previous windows, without contradicting the IMU more than its noise allows. Every point keeps its own timestamp and gets its own pose, so the motion during a sweep is compensated (deskewed).

Values on this pageThe values shown are those of settings/lidar-vertical.toml, tuned on datasets 42 and 43 (handheld L2, about 893 Hz IMU, 64k points/s) and on a static recording. The measurements behind them are in openspec/changes/archive/2026-09-30-gyro-bias-estimation/baseline.md.

The run command is lidar_odometry_step_1 <input_folder> settings/lidar-vertical.toml <output_folder>. The output folder receives scan_lio_N.laz (the map), trajectory_lio_N.csv (one pose per IMU sample, 4×3 matrix plus the raw IMU angles), session.mjs with session_poses.mrp (loadable in HDMapping), the parameters used (HDMapping_params_*.toml) and HDMapping_results_*.json (trajectory length, grid info, and the gyro bias per window in gyro_bias_per_window).

The pipeline

Steps 5 to 8 repeat for every window (dashed arrow). The sections below follow one point through all of them.

  1. Loading and filtering the points

    load_data / load_point_cloud · app/lidar_odometry.cpp, app/lidar_odometry_utils.cpp

    Each point is read with its position in the sensor frame, its intensity and its timestamp. Then:

    • If a calibration .json exists, the point is transformed with that LiDAR's extrinsics. Otherwise it is shifted by the LiDAR→IMU lever arm (translation only), so that points and IMU share one origin. The L2 data from dLidar is already in the IMU axes (NWU: x forward, y left, z up).
    • Points with timestamp 0 are dropped.
    • Points whose horizontal distance √(x²+y²) in the sensor frame is below filter_threshold_xy_inner (the handle, your hand, the housing) or above filter_threshold_xy_outer are dropped.
    • The points of each file are sorted by time. The IMU CSVs are read, merged and sorted by time.
    filter_threshold_xy_innerfilter_threshold_xy_outerlidar_imu_lever_arm_*

  2. An orientation for every IMU sample

    calculate_trajectory · app/lidar_odometry.cpp

    A Madgwick-type filter (Fusion AHRS, 6-axis, no magnetometer) integrates the gyro, and uses the accelerometer's gravity direction to correct roll and pitch. Heading (yaw) has no absolute reference, so it drifts with the gyro bias. That is what the LiDAR optimization and the bias estimation fix later. The accelerometer correction is switched off whenever |a| is outside 0.9–1.1 g (hard accelerations).

    If use_remove_imu_bias_from_first_stationary_scan is on, the median gyro value of the first 1000 samples is subtracted as bias, but only if the total gyro variance there is below 5 (°/s)². Handheld recordings usually fail that check ("Excessive movement detected") and continue with zero bias.

    Result: a trajectory map timestamp → rotation with one entry per IMU sample (about 1.1 ms apart). These are the trajectory nodes. Their positions are still zero at this stage.

    ahrs_gainfusionConvention*use_remove_imu_bias_from_first_stationary_scan

  3. Windows and a pose for every point

    compute_step_1 · app/lidar_odometry.cpp
    • The first threshold_initial_points points are set aside to build the initial map (step 4). Nodes before the time of the last of these points are skipped.
    • The remaining nodes are cut into windows of threshold_nr_poses consecutive nodes (360 ≈ 0.4 s at 893 Hz). A leftover shorter than a full window is dropped.
    • Every point in the window's time span is attached to the node just before its timestamp (its index_pose), but only if that node is at most 10 ms earlier. Otherwise the point is dropped. Windows with ≤ 1000 points are dropped.
    • Two copies are cached on disk (<input>/cache): all points (for export) and a voxel-decimated copy that keeps the first point per decimation-sized cube (used in the optimization).

    From here on, a point is always used as pose(index_pose) × point. Correcting a node's pose moves exactly the points recorded in that ~1 ms, and this is how motion during the scan is compensated.

    threshold_initial_pointsthreshold_nr_posesdecimation

  4. The initial map

    compute_step_2 (start) · app/lidar_odometry_utils_optimizers.cpp

    The set-aside initial points are transformed with the first pose only (no per-point motion compensation) and inserted into two NDT grids. Space is divided into cubes (0.15 m "indoor" and 0.4 m "outdoor" grid), and each cube stores the mean and covariance of the points in it, i.e. a small Gaussian that describes the local surface. A cube with 3 or more points also gets a normal vector facing the sensor.

    Because this map is not motion-compensated, stand still for the first second or two if you can. The first window is registered against this map, so its misfit is not allowed to affect the gyro bias estimate.

    in_out_params_indoor.resolution_*in_out_params_outdoor.resolution_*threshold_initial_points

  5. Initial guess for the next window

    compute_step_2 · app/lidar_odometry_utils_optimizers.cpp
    • The window's first node is placed exactly on the previous window's last node.
    • Rotations follow the IMU's relative rotations between nodes, minus the gyro bias estimated so far (bias × Δt per step).
    • Positions follow a constant velocity: the velocity over the last 20 nodes of the previous window (use_motion_from_previous_step). The IMU accelerometer is not integrated for position.

    This guess is also stored as the motion model: the IMU "measurement" the optimizer compares against.

    use_motion_from_previous_stepuse_gyro_bias_estimation

  6. Window optimization

    optimize_lidar_odometry · app/lidar_odometry_utils_optimizers.cpp

    The unknowns are the 6 pose parameters (x, y, z, ω, φ, κ) of every node of the window, plus 3 gyro-bias values: 6 × 360 + 3 = 2163 numbers. Each Levenberg–Marquardt iteration builds one least-squares system from these terms:

    • Point to map (NDT, fine grid): every decimated point with 3-D distance between min_distance_lidar and max_distance_lidar is transformed with its node's pose and looked up in the 0.15 m grid. Its distance to that cube's Gaussian, weighted by the inverse covariance, is minimized. Points hitting a cube whose normal faces away from the sensor, or whose covariance is degenerate, are skipped.
    • Point to map (NDT, coarse grid): the same with the 0.4 m grid, for points between min_distance_lidar_outdoor_grid and max_distance_lidar.
    • IMU motion model: between consecutive nodes, the relative pose should match the guess. Translation is held tightly (*_x/y/z_1_sigma_m). Rotation may deviate by max(k × ARW × √Δt, floor) per axis, i.e. about what the gyro can drift in that Δt (time-scaled rotation prior). The gyro bias enters here: the IMU step is corrected by −bias × Δt.
    • Velocity continuity: the velocity may only change as much as acc_1_sigma_mps2 allows, including across the boundary to the previous window.
    • Fixed start: node 0 is locked to the previous window's end (fix_origin sigmas, 1e-6).
    • Bias prior: the bias stays near the previous window's estimate, within its uncertainty grown by the bias random walk.

    The system is solved with a sparse Cholesky factorization. Up to nr_iter iterations run; the damping starts at lm_factor_initial and is multiplied by 10 every 10 iterations (pose unknowns only). A window is also stopped once it has run for longer than real_time_threshold_seconds.

    nr_iterlm_factor_initialmin_distance_lidarmax_distance_lidarmotion_model_uncertainty.*gyro_arw_*rotation_sigma_*

  7. Hand-off and gyro bias

    compute_step_2 · app/lidar_odometry_utils_optimizers.cpp

    The last node of a window has no points, and the ones just before it have very few. Left free, they can spin by several degrees, and the next window would inherit that error permanently, which shows up as rotated "ghost" copies of walls. So after the optimization, the last handoff_tail_nodes nodes are recomputed from the last well-constrained node using the bias-corrected IMU rotation and the optimized velocity. The next window starts from that recomputed end.

    The window's bias estimate and its uncertainty become the prior for the next window, and they are printed and written to the results JSON.

    handoff_tail_nodesgyro_bias_*

  8. Map update

    compute_step_2 · app/lidar_odometry_utils_optimizers.cpp

    The window's decimated points, now transformed with their optimized poses, are added to both NDT grids (the Gaussians are updated incrementally). The map therefore grows with the whole recording. Once the travelled distance exceeds sliding_window_trajectory_length_threshold, the map is rebuilt from the most recent half of the points, which bounds memory on long runs.

    sliding_window_trajectory_length_threshold

  9. Export

    save_result · app/lidar_odometry.cpp

    All original points (not the decimated ones) are transformed with their own optimized node pose. Points whose sensor-frame distance is below threshould_output_filter are removed from the export. Windows are grouped into chunks of 51, and each chunk becomes one scan_lio_N.laz, expressed relative to the chunk's first pose, with that pose stored in the session files. A final chunk with ≤ min_counter_concatenated_trajectory_nodes windows is not written.

    threshould_output_filtermin_counter_concatenated_trajectory_nodes
Consistency pass: GUI onlyThe [consistency] refinement (a global smoothing and point-cloud consistency optimization over the whole trajectory) is only run from the GUI. The command-line mode goes straight from step 8 to the export and ignores these parameters.

Parameter reference

One table per TOML section, in the order that matters most. Values are those of settings/lidar-vertical.toml. Labels: key strongly affects results, GUI only not used by the command-line mode, inactive read but has no effect with the current settings or code. Missing keys fall back to built-in defaults, and every run saves the complete set it used to HDMapping_params_*.toml.

[filter_points]

ParameterValueMeaning
filter_threshold_xy_inner key0.35 mAt load: drop points closer than this horizontal radius (√(x²+y²), sensor frame). Removes the operator's hand and body and the housing. Points on the operator that move with the sensor pull the solution toward "no rotation", so this must cover them.
filter_threshold_xy_outer25.0 mAt load: drop points beyond this horizontal radius. The L2 reaches 30 m at 90 % reflectivity and 15 m on dark rock.
decimation key0.03 mVoxel size for the copy of each window used in the optimization (the first point per cube is kept). Smaller means more points, slower but more constraints. The export always uses all points.
threshould_output_filter0.4 mExport only: drop points closer than this 3-D distance to the sensor.
min_counter_concatenated_trajectory_nodes10Export only: the last output chunk is written only if it contains more than this many windows (1 window ≈ 0.4 s).

[lidar_odometry_control]

ParameterValueMeaning
threshold_nr_poses key360Nodes (IMU samples) per window: 360 ≈ 0.4 s at 893 Hz. Longer windows give more context but are slower (cost grows with the square) and adapt the bias more slowly. Tested 720: slightly sharper, about 50 % slower.
threshold_initial_points60000Points used for the initial map (≈ 1 s of L2 data). Not motion-compensated, so ideally recorded while standing still.
nr_iter100Maximum Levenberg–Marquardt iterations per window.
lm_factor_initial5.0Initial LM damping on the pose unknowns, ×10 every 10 iterations. Larger values mean smaller, safer steps.
min_distance_lidar0.15 mPoints closer than this (3-D) are not used against the fine NDT grid. Blind zone and self-reflections.
min_distance_lidar_outdoor_grid1.0 mPoints closer than this are not used against the coarse grid.
max_distance_lidar25.0 mPoints farther than this are not used in the optimization (both grids). Far points are noisier but constrain rotation strongly.
use_motion_from_previous_steptrueInitial position guess from the previous window's velocity (constant-velocity model). If false, the positions start where the IMU chain puts them, i.e. without motion.
sliding_window_trajectory_length_threshold200.0 mAfter this much travelled distance, the map is rebuilt from the newer half of its points. Lower it for very long recordings to bound memory.

[in_out_params_indoor] and [in_out_params_outdoor]

ParameterValueMeaning
indoor resolution_X/Y/Z key0.15 mCube size of the fine NDT grid. It should be a few times the point noise (≤ 2 cm) and small enough to separate nearby surfaces in narrow passages. Too small gives too few points per cube.
outdoor resolution_X/Y/Z0.4 mCube size of the coarse grid, which gives robust, large-scale alignment for points beyond 1 m.
bounding_box_*, number_of_buckets*, bounding_box_extension inactive0Grid bookkeeping fields carried in the file format. The odometry uses a hashed grid of unlimited extent, so these are ignored.

[motion_model_uncertainty]

How far each node may deviate from the IMU-based guess relative to its neighbour. Small sigma = trust the IMU, large sigma = let the LiDAR decide.

ParameterValueMeaning
use_time_scaled_rotation_sigma keytrueRotation sigma per step = max(k · ARW · √Δt, floor), per axis. It matches how a gyro actually drifts: a 0.1 ms step gets far less freedom than a 2 ms step. If false, the constant *_om/fi/ka_1_sigma_deg below are used per node.
gyro_arw_x / y / z_deg_sqrt_s0.028 / 0.042 / 0.057Gyro angle random walk (noise density) in °/√s, measured on a 17 s static L2 recording. Axes map to ω (roll), φ (pitch), κ (yaw).
rotation_sigma_inflation_k key4.0Multiplier on the pure gyro noise, which covers timestamp jitter, vibration and model error. Tuned: 12 leaves visible jitter, 4 gives the sharpest maps, 2 and 1 over-trust the IMU and blur walls.
rotation_sigma_floor_deg0.002°Lower bound of the per-step rotation sigma, so that near-zero Δt does not produce infinite weights.
lidar_odometry_motion_model_x/y/z_1_sigma_m1e-4 mAllowed deviation of the relative translation between consecutive nodes from the constant-velocity guess. Very tight: position changes mainly through the velocity prior and the first node.
lidar_odometry_motion_model_acc_1_sigma_mps21.0 m/s²Velocity-continuity prior: how fast the velocity may change, also across window boundaries (avoids velocity kinks every window). 0 disables it.
lidar_odometry_motion_model_om/fi/ka_1_sigma_deg inactive0.1 / 0.1 / 0.15°Constant rotation sigma per node, only used when use_time_scaled_rotation_sigma = false. These values caused the ghost walls: every ~1 ms node could turn 0.15°.

Tuning cheat sheet

SymptomLikely causeWhat to change
Walls appear as several rotated copiesHeading error handed from window to windowKeep use_time_scaled_rotation_sigma on and handoff_tail_nodes > 0. Check that the IMU timestamps are strictly increasing.
Walls thick or fuzzyPer-node rotation jitterLower rotation_sigma_inflation_k (not below about 2), or check decimation.
Map rotates slowly over the recordingGyro biasKeep use_gyro_bias_estimation on. Check the bias track in the results JSON.
Bias clamp warningsPoor LiDAR geometry, or points on the operatorRaise filter_threshold_xy_inner / min_distance_lidar, and check the first second of the recording.
Feature-poor tunnel driftsToo few constraintsLower decimation, raise max_distance_lidar, or try threshold_nr_poses = 720.
Results differ between runsMultithreadinguseMultithread = false.

Use tools/eval_odometry.py to compare runs objectively: jitter, heading agreement with the gyro, end-of-window spikes, and map sharpness (occupied cells in a height section). See tools/README.md.

Known limitations

  • Initial map is not motion-compensated. The first ~60k points are placed with the first pose only.
  • Consistency pass is GUI only, so the command-line output skips it.
  • Map decimation on rebuild has no effect. When the map is rebuilt after sliding_window_trajectory_length_threshold, the result of decimate() is discarded, so the rebuilt map uses all points of the newer half.
  • dLidar IMU timestamps. Current recordings are strictly increasing, but samples inside a batch are stamped only about 0.02 ms apart instead of about 1.13 ms. Heading is unaffected, but most steps hit rotation_sigma_floor_deg. This should be fixed in dLidar.
  • Last partial output chunk. It is dropped if it has ≤ min_counter_concatenated_trajectory_nodes windows.
