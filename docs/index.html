What the odometry does with the points it reads

A reference for dMapper: how every LiDAR point travels from the recorder's LAZ file to the final map, and what each parameter in settings/lidar-vertical.toml controls.

The program is a LiDAR-inertial odometry. The IMU gives a fast but drifting estimate of how the sensor rotated. The LiDAR sees the surroundings, which do not move. The program cuts the recording into short windows of about 0.4 s. Each window's trajectory is adjusted until its points line up with the map built from all previous windows, without contradicting the IMU more than its noise allows. Every point keeps its own timestamp and gets its own pose, so the motion during a sweep is compensated (deskewed).

Values on this pageThe values shown are those of settings/lidar-vertical.toml, tuned on datasets 42 and 43 (handheld L2, about 893 Hz IMU, 64k points/s, short cave walks), on a static recording and on b1 (a 4-minute walk over three floors of a building with a one-sided corridor, stairwells and revisited rooms). The measurements behind them are in openspec/changes/archive/2026-09-30-gyro-bias-estimation/baseline.md.

Inputs and outputs

The run command is dMapper <input_folder> settings/lidar-vertical.toml <output_folder>. The output folder receives scan_lio_N.laz (the map), trajectory_lio_N.csv (one pose per IMU sample, 4×3 matrix plus the raw IMU angles), session.mjs with session_poses.mrp (loadable in HDMapping), the parameters used (dMapper_params_*.toml) and dMapper_results_*.json (trajectory length, grid info, and the gyro bias per window in gyro_bias_per_window).

To rerun only loop closure, consistency and saving, set save_odometry_snapshot = true and add --from-snapshot <file> to the command, see [lidar_odometry_debug_info].

The pipeline

Steps 5 to 8 repeat for every window (dashed arrow). The sections below follow one point through all of them.

  1. Loading and filtering the points

    load_data / load_point_cloud · src/application/lidar_odometry.cpp, src/infrastructure/recording_folder_source.cpp

    Each point is read with its position in the sensor frame, its intensity and its timestamp. Then:

    • Each point is shifted by the LiDAR→IMU lever arm (translation only), so that points and IMU share one origin. The L2 data from dLidar is already in the IMU axes (NWU: x forward, y left, z up).
    • Points with timestamp 0 are dropped.
    • Points whose horizontal distance √(x²+y²) in the sensor frame is below filter_threshold_xy_inner (the handle, your hand, the housing) or above filter_threshold_xy_outer are dropped.
    • The points of each file are sorted by time. The IMU CSVs are read, merged and sorted by time.
    filter_threshold_xy_innerfilter_threshold_xy_outerlidar_imu_lever_arm_*

  2. An orientation for every IMU sample

    calculate_trajectory · src/application/lidar_odometry.cpp

    A Madgwick-type filter (Fusion AHRS, 6-axis, no magnetometer) integrates the gyro, and uses the accelerometer's gravity direction to correct roll and pitch. Heading (yaw) has no absolute reference, so it drifts with the gyro bias. That is what the LiDAR optimization and the bias estimation fix later. The accelerometer correction is switched off whenever |a| is outside 0.9–1.1 g (hard accelerations).

    If use_remove_imu_bias_from_first_stationary_scan is on, the median gyro value of the first 1000 samples is subtracted as bias, but only if the total gyro variance there is below 5 (°/s)². Handheld recordings usually fail that check ("Excessive movement detected") and continue with zero bias.

    Result: a trajectory map timestamp → rotation with one entry per IMU sample (about 1.1 ms apart). These are the trajectory nodes. Their positions are still zero at this stage.

    ahrs_gainfusionConvention*use_remove_imu_bias_from_first_stationary_scan

  3. Windows and a pose for every point

    compute_step_1 · src/application/lidar_odometry.cpp
    • The first threshold_initial_points points are set aside to build the initial map (step 4). Nodes before the time of the last of these points are skipped.
    • The remaining nodes are cut into windows of threshold_nr_poses consecutive nodes (360 ≈ 0.4 s at 893 Hz). A leftover shorter than a full window is dropped.
    • Every point in the window's time span is attached to the node just before its timestamp (its index_pose), but only if that node is at most 10 ms earlier. Otherwise the point is dropped. Windows with ≤ 1000 points are dropped.
    • Two copies are cached on disk (<input>/cache): all points (for export) and a voxel-decimated copy that keeps the first point per decimation-sized cube (used in the optimization).

    From here on, a point is always used as pose(index_pose) × point. Correcting a node's pose moves exactly the points recorded in that ~1 ms, and this is how motion during the scan is compensated.

    threshold_initial_pointsthreshold_nr_posesdecimation

  4. The initial map

    optimize_windows (start) · src/application/run_odometry.cpp

    The set-aside initial points are transformed with the first pose only (no per-point motion compensation) and inserted into two NDT grids. Space is divided into cubes (0.15 m "indoor" and 0.4 m "outdoor" grid), and each cube stores the mean and covariance of the points in it, i.e. a small Gaussian that describes the local surface. A cube with 3 or more points also gets a normal vector facing the sensor.

    Because this map is not motion-compensated, stand still for the first second or two if you can. The first window is registered against this map, so its misfit is not allowed to affect the gyro bias estimate.

    in_out_params_indoor.resolution_*in_out_params_outdoor.resolution_*threshold_initial_points

  5. Initial guess for the next window

    optimize_windows · src/application/run_odometry.cpp
    • The window's first node is placed exactly on the previous window's last node.
    • Rotations follow the IMU's relative rotations between nodes, minus the gyro bias estimated so far (bias × Δt per step).
    • Positions, with imu_always_on (lidar-vertical): the accelerometer integrated from the start velocity carried over from the previous window, with that window's gravity and acceleration offset (integrate_window_translations). A window at rest keeps a motionless guess. Without it: a constant velocity, the velocity over the last 20 nodes of the previous window (use_motion_from_previous_step).

    This guess is also stored as the motion model: the IMU "measurement" the optimizer compares against.

    use_motion_from_previous_stepuse_gyro_bias_estimationimu_always_on

  6. Window optimization

    optimize_lidar_odometry · src/domain/scan_to_map.cpp

    The unknowns are the 6 pose parameters (x, y, z, ω, φ, κ) of every node of the window, plus 3 gyro-bias values: 6 × 360 + 3 = 2163 numbers. With imu_always_on there are 9 more: the acceleration offset and the velocity at the window's start and end. Each Levenberg–Marquardt iteration builds one least-squares system from these terms:

    • Point to map (NDT, fine grid): every decimated point with 3-D distance between min_distance_lidar and max_distance_lidar is transformed with its node's pose and looked up in the 0.15 m grid. Its distance to that cube's Gaussian, weighted by the inverse covariance, is minimized. Points hitting a cube whose normal faces away from the sensor, or whose covariance is degenerate, are skipped.
    • Point to map (NDT, coarse grid): the same with the 0.4 m grid, for points between min_distance_lidar_outdoor_grid and max_distance_lidar.
    • IMU motion model: between consecutive nodes, the relative pose should match the guess. Translation is held tightly (*_x/y/z_1_sigma_m). Rotation may deviate by max(k × ARW × √Δt, floor) per axis, i.e. about what the gyro can drift in that Δt (time-scaled rotation prior). The gyro bias enters here: the IMU step is corrected by −bias × Δt.
    • Velocity continuity: the velocity may only change as much as acc_1_sigma_mps2 allows, including across the boundary to the previous window. The previous window's final velocity is measured over its last 20 nodes; if it is faster than max_prior_velocity_mps, it is not used, and the window starts from 0 m/s without that link.
    • Accelerometer, always on (imu_always_on, lidar-vertical): in every window from the second on, the change of velocity between nodes about 10 ms apart must match R · f − g minus the acceleration offset e. The term also moves the node rotations, so a tilt that leaks gravity into the acceleration is corrected in the attitude, not smeared over hundreds of positions. Each term is weighted by the sensor's noise: σ² = imu_accel_noise_density_mps2_sqrt_hz² / τ + imu_accel_floor_sigma_mps2² over its span τ. The second part is the vibration floor: walking shakes the handheld scanner far more than the noise measured at rest, and the floor keeps those shakes from being read as motion. The start and end velocities are unknowns with priors carried from window to window, like the gyro bias. A window at rest gets a zero-velocity measurement. A term whose span is stretched by an IMU gap is dropped. In a blind passage the window keeps the speed the accelerometer measures, instead of stalling when the LiDAR can't see it move (see [imu_translation]).
    • Accelerometer, blind stretches only (when imu_always_on is false): when the previous window's points left one translation direction unconstrained (a corridor turnaround, a stairwell), the velocity-continuity term is replaced by the measured acceleration: the change of velocity between nodes about 10 ms apart must match R · f − g minus an acceleration offset e. e is 3 extra unknowns that absorb tilt and accelerometer bias errors, carried from window to window like the gyro bias, and calibrated from the LiDAR trajectory while the geometry is good. The translation prior is loosened to imu_degenerate_translation_sigma_m in those windows, and the term switches off after imu_degenerate_max_duration_s. See [imu_translation].
    • Fixed start: node 0 is locked to the previous window's end (fix_origin sigmas, 1e-6).
    • Bias prior: the bias stays near the previous window's estimate, within its uncertainty grown by the bias random walk.

    The system is solved with a sparse Cholesky factorization. Up to nr_iter iterations run; the damping starts at lm_factor_initial and is multiplied by 10 every 10 iterations (pose unknowns only). A window stops early when the sum of all parameter updates of one iteration falls below convergence_delta_threshold (default 1e-12, which is practically never reached, so all iterations run), or once it has run for longer than real_time_threshold_seconds. Only the band of the normal matrix that can hold values (neighbouring nodes and the bias unknowns) is converted to sparse form each iteration.

    nr_iterconvergence_delta_thresholdlm_factor_initialmin_distance_lidarmax_distance_lidarmotion_model_uncertainty.*gyro_arw_*rotation_sigma_*

  7. Hand-off and gyro bias

    optimize_windows · src/application/run_odometry.cpp

    The last node of a window has no points, and the ones just before it have very few. Left free, they can spin by several degrees, and the next window would inherit that error permanently, which shows up as rotated "ghost" copies of walls. So after the optimization, the last handoff_tail_nodes nodes are recomputed from the last well-constrained node using the bias-corrected IMU rotation and the optimized velocity. The next window starts from that recomputed end.

    The window's bias estimate and its uncertainty become the prior for the next window, and they are printed and written to the results JSON.

    handoff_tail_nodesgyro_bias_*

  8. Map update

    optimize_windows · src/application/run_odometry.cpp

    The window's decimated points, now transformed with their optimized poses, are added to both NDT grids (the Gaussians are updated incrementally). The map therefore grows with the whole recording. Once the travelled distance exceeds sliding_window_trajectory_length_threshold, the map is rebuilt from the most recent half of the points, voxel-decimated with decimation, which bounds memory on long runs. With the default 200 m this happens rarely on handheld recordings.

    sliding_window_trajectory_length_threshold

  9. Export

    save_result · src/application/lidar_odometry.cpp

    All original points (not the decimated ones) are transformed with their own optimized node pose. Points whose sensor-frame distance is below threshould_output_filter are removed from the export. Windows are grouped into chunks of 51, and each chunk becomes one scan_lio_N.laz, expressed relative to the chunk's first pose, with that pose stored in the session files. The remaining windows form a final, shorter chunk, which is written if it has more than min_counter_concatenated_trajectory_nodes windows (default 0, so it is always written).

    With export_merged_laz = true all chunks are additionally written into one scan_lio_merged.laz in world coordinates.

    threshould_output_filtermin_counter_concatenated_trajectory_nodesexport_merged_laz
Loop closure (after step 8, before the consistency pass)With use_loop_closure = true the run (command line and GUI alike) corrects the finished trajectory when you come back to a place you have already scanned (src/application/loop_closure.cpp):
  1. The windows are grouped into segments of loop_closure_segment_windows windows (6 ≈ 2.4 s), each with its points in world coordinates. Until 2026-10-15 a segment had 12 windows (≈ 5 s); a turn of the path then often lay inside one rigid segment, and on 44 the graph twisted the out-and-back gallery by up to 2.4°.
  2. Revisit candidates: for every segment, the earlier segments with at least loop_closure_min_path_m walked in between, whose centre lies within min(loop_closure_search_radius_m, loop_closure_radius_per_path × that path) horizontally and loop_closure_max_vertical_offset_m vertically (so different floors are not confused), longest path first. The path counts a step only once the position moved 0.1 m, so standing still adds nothing; a dead end walked out and back qualifies however short the time, neighbouring segments and places seen from afar don't, and a near revisit does not take the place of a far one (the loop closure of a whole round). Up to loop_closure_candidates of them are registered, chosen to differ, in this order: the nearest one, the longest-path one, the nearest at least 3 segments away from the nearest, and the longest-path one at least 3 segments away from the longest-path one (a smaller limit keeps both kinds). Of the accepted registrations, up to loop_closure_edges_per_segment become loop edges: the best of the near ones and the best of the far ones by overlap after the refinement, both only if their earlier segments are at least 3 apart (otherwise the better one). Until 2026-10-14 revisits had to be loop_closure_min_time_gap_s = 30 s apart, which never compared the gallery of 44 (walked out and back in 10–25 s); an old parameter file with that key still loads, the key is ignored.
  3. Registration: the later segment is aligned to the earlier one and its neighbours, first by a voxel-overlap search over yaw (±10°) and translation (±loop_closure_max_correction_m), then by point-to-distribution refinement. It is accepted only if at least loop_closure_min_fitness of its points overlap the earlier visit, the overlap did not get worse, and the correction stays within the search range and 15°.
  4. Pose graph: the segment poses are optimized with odometry edges between consecutive segments and the accepted loop edges, the first segment fixed. A step is kept only if it lowers the graph's error (damped otherwise). Every loop edge, on the same floor and between floors, is weighted by what its registration determines (its NDT normal matrix mapped into the edge, scaled so that the best-determined translation gets loop_closure_edge_sigma_m; see loop_closure_cross_floor_max_vertical_m below); an edge whose registration information is unusable keeps the fixed sigmas. A weak direction, such as along a corridor or the turn of a narrow passage, then pulls little, and the loop closure no longer invents turns the odometry didn't make. Then each loop edge is compared with the solution: of the edges that disagree by more than loop_closure_max_residual_m or loop_closure_max_residual_deg (in their weighted residual), the one whose removal lowers the error of the re-solved graph the most is a false match; it is dropped and the graph solved again, until all edges agree. One false edge would otherwise bend the trajectory by decimetres (on 44 a 3 m correction among neighbours of 2 m left a 60 cm ghost wall). The result is applied only if it is finite and no segment moved further than loop_closure_max_correction_m plus the largest accepted correction; otherwise it is discarded with a warning and the trajectory stays as it was.
  5. The correction of each segment is interpolated onto every trajectory node, so the trajectory bends smoothly instead of jumping.
The log lists every candidate with its overlap before/after and the correction, every dropped edge, and the residuals of the edges kept. Errors larger than the search range (for example a 20° heading failure) are rejected on purpose; they come from the odometry and have to be fixed there.
Optional: consistency pass (between steps 8 and 9)With use_consistency = true the run (command line and GUI alike) calls run_consistency after the odometry and loop closure, before the export. It re-optimizes the whole trajectory at once, num_constistency_iter times: every node is pulled towards a smooth trajectory (relative-pose prior between consecutive nodes), and points from all windows must agree with one NDT map built from the whole recording. This can remove residual misalignment between windows, such as a wall seen at the start and again at the end, but it is slow and it can also smear the trajectory if the smoothness prior is too strong. Two variants (use_mutliple_gaussian):
  • Consistency (false): one Gaussian per indoor-grid cube, rotation smoothness 0.1°, points closer than a hard-coded 1 m are ignored.
  • Consistency2 (true): several Gaussians per cube, one per time segment of 1M points (a cube needs ≥ 5 points in the segment), so different passes through the same place are matched against each other. Rotation smoothness 0.01°, points closer than consistency_min_distance are ignored.
See Fixes and map sharpness for measured effects.

Parameter reference

One table per TOML section, in the order that matters most. Values are those of settings/lidar-vertical.toml. Labels: key strongly affects results, GUI only only affects the GUI, inactive read but has no effect with the current settings or code. Missing keys fall back to built-in defaults, and every run saves the complete set it used to dMapper_params_*.toml.

[motion_model_uncertainty]

How far each node may deviate from the IMU-based guess relative to its neighbour. Small sigma = trust the IMU, large sigma = let the LiDAR decide.

ParameterValueMeaning
use_time_scaled_rotation_sigma keytrueRotation sigma per step = max(k · ARW · √Δt, floor), per axis. It matches how a gyro actually drifts: a 0.1 ms step gets far less freedom than a 2 ms step. If false, the constant *_om/fi/ka_1_sigma_deg below are used per node.
gyro_arw_x / y / z_deg_sqrt_s0.028 / 0.042 / 0.057Gyro angle random walk (noise density) in °/√s, measured on a 17 s static L2 recording. Axes map to ω (roll), φ (pitch), κ (yaw).

rotation_sigma_floor_deg0.002°Lower bound of the per-step rotation sigma, so that near-zero Δt does not produce infinite weights.
rotation_sigma_inflation_k_turn inactive0 (off)In windows turning faster than turn_rate_threshold_deg_s about the vertical, this replaces rotation_sigma_inflation_k, i.e. the gyro is trusted more in tight turns. [imu_translation]

Use of the accelerometer for the translation. Walking produces only about 0.2 m/s² of acceleration, while a 1° tilt error already leaves 0.17 m/s² of gravity in it, and position is its double integral. lidar-vertical therefore uses it always on, together with the attitude, the velocity and an acceleration offset estimated alongside, each term weighted by the sensor's noise plus a vibration floor. It needs the IMU and LiDAR timestamps to agree within a few milliseconds: on recordings whose IMU lagged by 50–80 ms (dLidar before its fix), the accelerometer term made results worse. Without imu_always_on, the accelerometer is used only where the LiDAR is blind in a direction, only for a limited time.

Best practices

Most of the map quality is decided while recording. The odometry can only correct what it can observe twice, so plan the walk so that every part of the building is seen again later.

Recording

  • Walk a loop on every floor. Come back to a place you have already scanned on the same floor (a room, a corridor junction, the stair landing) at least 30 s after the first visit, and pass within a few metres of where you walked before. Each such revisit lets loop closure pull that floor into line. A floor walked only once cannot be corrected: on b1 the 1st floor, walked once, stayed rotated by about 4.5° because the heading errors on the way down and back up the stairs cancelled out, so no loop exposed it. Recording 44, with loops on every floor, came out well aligned.
  • Close the loop on the floor, not only through the stairs. A revisit on another floor is not matched (loop_closure_max_vertical_offset_m = 1.5 m), so each floor needs its own revisit.
  • Pause at feature-rich spots briefly before and after long featureless stretches (one-sided corridors, open halls), so the distance across them is anchored at both ends.
  • Hold still for 3–5 s at the start, as the Unitree L2 data sheet asks. The initial map is not motion-compensated (see Known limitations). With imu_always_on, a window at rest also pins the velocity and the accelerometer offset. Keep yourself out of the scanner's near field in the first second. Short stops later on help in the same way.
  • Take stairs steadily and look around at each landing; stairwells are where the odometry is weakest.

Processing

  • Use the Release build with settings/lidar-vertical.toml, from the command line or loaded in the GUI (Start → Load parameters); both run the same stages, including loop closure and the consistency pass, and give the same result.
  • Recordings from the fixed dLidar (with timing0001.json) carry the sensor's own timestamps for both streams and need no repair. Older dLidar recordings have an IMU that lags the LiDAR by 20–80 ms: measure it with tools/imu_time_offset.py and correct it with tools/restamp_imu.py before processing (see tools/README.md).
  • Check the result per floor: walls seen on different passes should overlap as one surface. If a room appears twice or a floor is rotated, see the tuning cheat sheet.

Reading the result. Both variants pull every window towards one map of the whole recording, which removes the small offsets left between windows. Consistency sharpens both recordings, but its weaker smoothness prior (0.1°) lets the trajectory roughen by 2–4×. That does not blur the map, because each node is re-fitted to the points, but the trajectory is less smooth when used on its own. Consistency2 keeps the trajectory almost as smooth (0.01° prior) and matches Consistency on 43. On 42 it barely helps, because a short walk seldom revisits the same cubes in a different 1M-point segment. The heading agreement with the gyro is unchanged in all runs.

Recommendation. lidar-vertical.toml enables use_consistency. Set it to false when runtime matters more than map quality. Use Consistency (the default variant) for the sharpest map. Use Consistency2 on longer walks with loops or revisits, or when the trajectory itself is used downstream.

Known limitations

  • Initial map is not motion-compensated. The first ~60k points are placed with the first pose only.
  • A fragile window at the top of a stairwell (recording 44, t ≈ 86 s). In a fast turn onto the stairs, the scan-to-map match of one window can land about one step (0.3 m) off. The /fp:precise build passes it in every run tried, a /fp:fast build of the same code doesn't, and from there the odometry runs away (6 m apart at the end). So the result there still hinges on rounding. Diagnosed (2026-10-10): a map cell's mean is the first point that fell into it, so a sub-millimetre pose difference gives new cells other means and the next window matches against a slightly different map; and a point that leaves the map costs nothing, so a window can slide away from the surfaces. A fix is planned as its own change.
  • dLidar IMU timestamps. dLidar before its fix stamped the IMU samples from their arrival on the host: in bursts, and 20–80 ms later than the LiDAR points (recording 44: 79 ms at the start, 52 ms at the end). The settings tuned on such data compensated for the lag, and the accelerometer made results worse on it. The fixed dLidar writes the sensor's own timestamps for both streams (timing0001.json; 45f: residual offset under 2 ms). Older recordings are corrected with tools/restamp_imu.py; the unsynchronized originals must not be processed.
  • Stairwells. On b1 the heading drifted up to ~10° between floors with several settings, and the return from the 1st to the 2nd floor failed in some runs by 20–90°, which is beyond what loop closure accepts. Repaired timestamps avoided it in the tests; more multi-floor recordings are needed to tune this. On recording 44 the heading drifts 2–6° between floors in the stretch where nothing mapped before is in view; this is expected (the gyro bias is known to ±0.05°/s). The cross-floor edges correct it, but their tilt is not fully reliable: the stairs of two floors are not exactly alike, so a registration can be precise and still off by about a degree. On one run a lower floor came out tilted by 0.85° about x, and the storey heights vary by up to 19 cm between runs. The gallery drift of one run (about 50 cm) is odometry during that pass and is still open.
  • NDT cell normals. By default a map cell's normal is fixed from its first 3 points and its mean is its first point; neither is updated later. Many normals are wrong (60 % on a synthetic corridor), which makes the degeneracy test noisy and costs about 1 mm in the scan-to-map fit. use_exact_ndt_bucket_statistics = true fixes the statistics, but it is off: on recording 44 it marked 439 instead of 95 windows as degenerate with the current threshold, and the map was 5 % less sharp. See Degeneracy information.
  • Loop closure only corrects revisits it can register (≥ 50% overlap, ≤ 6 m, ≤ 15°).
  • Loop closure also moves a correct trajectory. On the synthetic two-lap recording of the unit tests (tests/loop_closure_test.cpp) it halves a second-lap drift, but a trajectory that is already exact is moved by up to 3 cm and 0.1°: every revisit registers with a residual of 1–3 cm, and the pose graph trusts loop edges to 5 cm. With points only within 6 m it accepted a wrong registration and moved the trajectory by 1.5 m; the overlap threshold alone does not catch that.
  • The consistency pass also moves a correct trajectory, on the same synthetic recording (tests/consistency_test.cpp): Consistency by up to 6 mm (spread evenly, the noise of the NDT fit), Consistency2 by up to 16 mm and 0.5°, mostly where the turn rate changes, because its 0.01° rotation smoothness resists any change of turn rate. Both remove offsets between windows.
