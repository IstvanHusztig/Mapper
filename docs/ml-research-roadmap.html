M1 · The big picture: learning is fitting

Goal
See that training a model is an optimization, the same kind of computation as dMapper's odometry, and what makes it different.
Read
T1, T2. Optional: Goodfellow et al., Deep Learning, chapter 5 (machine learning basics).
Do
E1: turn 44_diag.log into a table, plot it, and fit a straight line with the normal equations. Starter code (tested: it finds all 690 windows): 
import re
import numpy as np
import matplotlib.pyplot as plt

pattern = re.compile(
    r"window diagnostics (\d+): t ([\d.]+) s, dt ([\d.]+) s, iterations (\d+), delta (\S+), "
    r"start (\S+) (\S+) (\S+), guess move (\S+) (\S+) (\S+), result move (\S+) (\S+) (\S+), .*?"
    r"result-guess (\S+) (\S+) (\S+), info ratio (\S+)")
rows = []
with open(r"C:\Users\User\Downloads\dLidar\raw data\44_diag.log", encoding="utf-8", errors="replace") as f:
    for line in f:
        m = pattern.search(line)
        if m:
            rows.append([float(v.rstrip(",")) for v in m.groups()])
data = np.array(rows)
t, iterations, info_ratio = data[:, 1], data[:, 3], data[:, 17]
result_minus_guess = np.linalg.norm(data[:, 14:17], axis=1)    # how far the optimizer moved the guess [m]

fig, ax = plt.subplots(3, 1, sharex=True)
ax[0].plot(t, iterations); ax[0].set_ylabel("iterations")
ax[1].plot(t, info_ratio); ax[1].set_ylabel("info ratio")
ax[2].plot(t, result_minus_guess); ax[2].set_ylabel("|result - guess| [m]"); ax[2].set_xlabel("t [s]")
plt.show()

# a straight line result_minus_guess = w0 + w1 * info_ratio, solved with the normal equations
A = np.column_stack([np.ones_like(info_ratio), info_ratio])
w = np.linalg.solve(A.T @ A, A.T @ result_minus_guess)
print(w)
Then make a scatter plot of info_ratio against result_minus_guess with the line drawn in it. Does the line describe the cloud of points?
Check
What does dMapper's optimizer want, and what does training want? Why does the difference matter? dMapper wants the best poses for the data in hand. Training wants weights that also work on data the model has never seen. You can only measure that on data held out from training, which is where splits, validation and overfitting come from.
Why is the column of ones in A there? It is the intercept w0: without it, the line would be forced through the origin.
Why can't a sum of features express "large error when the info ratio is low and the turn is fast"? A sum adds each feature's effect independently. An "and" means that one feature's effect depends on the other's value, an interaction, which needs a product or another nonlinearity. Networks learn such nonlinearities.
You understand it when
you can explain to someone why fitting a line and running dMapper's LM step are the same kind of problem, and what training adds.

M2 · What a network computes

Goal
Compute a network's output by hand, so it stops being a black box.
Watch, then read
3Blue1Brown, "But what is a neural network?" (chapter 1 of the series), then T3.
Do
A forward pass with pencil and paper. The network has 2 inputs, 2 hidden ReLU neurons and 1 output:
x = (1, 2)    W₁ = [[0.5, −1], [1, 0.5]]    b₁ = (0, −1)    W₂ = (2, 3)    b₂ = 0.5    target y = 3
Compute z = W₁x + b₁, h = ReLU(z), ŷ = W₂·h + b₂ and the loss L = (ŷ − y)². Then check:
Solution z = (0.5·1 − 1·2 + 0,  1·1 + 0.5·2 − 1) = (−1.5, 1)
h = ReLU(z) = (0, 1): the first neuron is off
ŷ = 2·0 + 3·1 + 0.5 = 3.5
L = (3.5 − 3)² = 0.25
Keep your numbers: module 4 continues with them.
Check
Why is an activation function needed at all? Without it, every layer is a linear map, and a chain of linear maps is one linear map. The whole network would be no more than linear regression.
How many parameters does a 5 → 8 → 1 network have? 5·8 + 8 = 48 for the first layer, 8·1 + 1 = 9 for the second: 57.
Why do weights start random instead of zero? With equal weights, every neuron of a layer computes the same thing and receives the same gradient, so they stay identical forever. Randomness breaks the symmetry.
You understand it when
you can compute a small network's output by hand and say what each weight does.

M3 · Loss and gradient descent

Goal
Understand what the loss measures, and how the weights move to make it smaller.
Watch, then read
3Blue1Brown, "Gradient descent, how neural networks learn" (chapter 2), then T4 and T5.
Do
E2, part 1: type in the numpy network from T8 yourself, without copy-paste, and run it. Then change the learning rate to 0.001, 0.05 and 1.0 and plot the loss against the step for each. Say in one sentence what each curve shows.
Check
What noise does the mean squared error assume? Gaussian noise with the same σ for every example: MSE is that noise model's negative log-likelihood, up to constants.
In the loss (y − μ)²/(2σ²) + log σ, what stops the network from predicting a huge σ everywhere to excuse its errors? The log σ term. A large σ makes the first term small but the second large, and the sum is smallest when σ matches the real size of the errors.
What does a too-large learning rate look like in the loss curve? The loss jumps up and down or explodes instead of falling. It can also kill neurons for good, as module 4 shows.
Why do networks train with first-order methods instead of Levenberg–Marquardt? LM needs a P × P matrix for P weights. That is impossible for millions of weights, and minibatch noise spoils the curvature anyway. The gradient costs only a few forward passes. For tiny networks on a full dataset, second-order methods such as L-BFGS do work.
You understand it when
you can predict roughly what a loss curve will look like before you change the learning rate.

M4 · Backpropagation

Goal
Know exactly how the gradient of every weight is computed. This is the core of all of deep learning.
Watch, then read
3Blue1Brown, "What is backpropagation really doing?" and "Backpropagation calculus" (chapters 3–4), then T6. Then the most valuable single resource on this page: Karpathy, "The spelled-out intro to neural networks and backpropagation: building micrograd" (the first video of Zero to Hero). Code along with it.
Do
1. The backward pass on paper, on the M2 example, with the formulas of T6. Compute ∂L/∂ŷ, ∂L/∂W₂, ∂L/∂h, ∂L/∂z and ∂L/∂W₁.
Solution ∂L/∂ŷ = 2(3.5 − 3) = 1
∂L/∂W₂ = 1 · h = (0, 1)    ∂L/∂b₂ = 1
∂L/∂h = W₂ · 1 = (2, 3)
∂L/∂z = (2·0, 3·1) = (0, 3): the first neuron was off (z = −1.5), so no gradient passes through it
∂L/∂W₁ = ∂L/∂z · xᵀ = [[0, 0], [3, 6]]    ∂L/∂b₁ = (0, 3)
2. One gradient-descent step with learning rate 0.01, then the forward pass again.
Solution W₂ = (2, 2.99), b₂ = 0.49, second row of W₁ = (0.97, 0.44), b₁ = (0, −1.03)
z = (−1.5, 0.82), h = (0, 0.82), ŷ = 2.99·0.82 + 0.49 = 2.9418
L = 0.0034, down from 0.25: one step, and the error fell by a factor of 70.
3. The same step with learning rate 0.1.
Solution, and the lesson The second row of W₁ becomes (0.7, −0.1) and b₁ = (0, −1.3), so z = (−1.5, −0.8) and h = (0, 0). Both neurons are now off, ŷ = b₂ = 0.4, and L = 6.76, 27 times worse. Worse still, with both neurons off, every gradient into W₁ is zero, so gradient descent can never switch them back on. This is a "dead ReLU": a too-large step can permanently disable part of a network.
4. E2, part 2: add a gradient check to your numpy network. For five weights, compare your backprop gradient with (L(w+ε) − L(w−ε)) / 2ε, with ε = 10⁻⁵.
Check
Why does backpropagation cost only a few forward passes, however many weights there are? Every step backward reuses the result of the step after it (the chain rule), and the forward pass has stored the intermediate values. Each weight's derivative is one multiplication away from quantities already computed.
Why do you need to store z during the forward pass? The backward pass needs to know where the ReLU was active (z > 0), and the layer inputs (x, h) to form the weight gradients.
You understand it when
your gradient check agrees to about six digits, and you can explain why the dead ReLU in step 3 can never recover.

M5 · Generalisation: fooling yourself, and how not to

Goal
Learn to measure honestly. With dMapper's data, this matters more than any choice of model.
Read
T7. Optional: Goodfellow et al., chapter 7 (regularisation); Hastie et al., chapter 7 (model assessment).
Do
E4, on the E1 table: predict |result − guess| from the other columns with a small model (for example scikit-learn's MLPRegressor), with two splits: (a) 80 % of the windows drawn at random for training; (b) the first 80 % of the route for training, the last 20 % for validation. Compare the validation errors of (a) and (b). Then shrink and grow the network and watch training and validation error move apart.
Check
Training error 0.01, validation error 0.30. What is happening? Overfitting: the model has learned the training examples, not the pattern. Make the model simpler, regularise it, or get more data.
Why does split (a) look better than split (b), and which one tells the truth? Neighbouring windows are nearly identical, so a random split puts near-copies of the validation windows into training. The model recognises them instead of predicting. Split (b) is the honest one, and leaving out a whole recording is more honest still.
What is weight decay in terms of probability? A Gaussian prior on the weights, centred on zero: the same idea as dMapper's priors, which pull a state toward its expected value unless the data says otherwise.
When may you look at the test set? Once, at the very end. Anything chosen after looking at it has been tuned on it, and the test result is no longer an honest estimate.
You understand it when
you distrust a good result until you know how the data was split.

M6 · PyTorch: what the tool does for you

Goal
Use PyTorch knowing what it does behind the scenes, and why it is worth its install size.
Read
T8, then the PyTorch tutorial "Learn the Basics" (tensors, autograd, building a model, optimization). If you watched Karpathy's micrograd video in M4, you have already built a tiny PyTorch yourself.
Do
E3: run the PyTorch version of your M3 network and compare its loss curve with your numpy one: same data, same start. Then switch to the uncertainty-predicting version from T8. To give it something to learn, make the toy data's noise grow with |x₁|. Plot the predicted σ against x₁.
Check
What exactly happens in loss.backward()? During the forward pass, PyTorch recorded every operation as a graph. backward() walks that graph from the loss back to the weights, applies each operation's local derivative (the chain rule of M4), and adds each weight's gradient to its .grad.
Why is opt.zero_grad() needed every step? Gradients are added to .grad, not overwritten. Without clearing, each step would use the sum of all previous gradients.
What does PyTorch give you that writing it by hand doesn't? And what does it not give you? It gives you any loss and any model without deriving a single gradient, plus ready-made optimizers. It does not give you understanding of what goes on (that was M4), and it isn't needed to use a trained model: the C++ forward pass is just multiplications and additions.
You understand it when
you could rewrite any small PyTorch training loop in numpy, slowly, and know which line does what.

M7 · Trees and Bayesian optimization

Goal
Know the two classical methods that the roadmap ranks above neural networks for dMapper's current situation.
Watch, then read
StatQuest (Josh Starmer) on decision trees and on gradient boosting (regression), then T9 and T10. Optional: the Optuna tutorial.
Do
E5: on your E4 task, compare gradient boosting with your MLP, both with split (b). E6: let Optuna minimise a noisy toy function, plot where it sampled, and watch it switch from exploring to exploiting.
Check
What does each new tree in gradient boosting learn? What the trees so far still get wrong: their residuals for squared loss, and in general the negative gradient of the loss. Each tree's contribution is shrunk by a learning rate.
Why can't a tree model extrapolate? Its output is a constant per leaf. Beyond the range of the training data, it just repeats the value of the outermost leaf.
What two things does a Gaussian-process surrogate tell Bayesian optimization, and how are they used? A predicted quality and an uncertainty for every untried setting. The acquisition function trades them off: it tries settings that look good (exploitation) or that are very uncertain (exploration).
Why is Bayesian optimization a good fit for tuning dMapper's TOML settings? Few settings, no gradient, a noisy result, and every evaluation costs a full run. It is built for exactly that.
You understand it when
you can say for a given problem whether you would reach for trees, a network or Bayesian optimization, and why.

Goal

Read and watch

How does PointNet handle the fact that points have no order? The same MLP is applied to every point, and the points are combined with max-pooling, which gives the same result in any order.
Why does reinforcement learning need so many episodes? The reward comes late (which decision earned it?), every action must be tried many times, including bad ones, and the policy's own changes make its old experience stale. One dMapper episode is a 1.5–20 min run.

That is epistemic uncertainty: the model doesn't know, and it can't tell from its own σ. A cave after training on buildings is exactly this case.

T1 · Learning is optimization — and you already know it

Training a model means: choose numbers (the parameters or weights θ) so that a function f(x; θ) produces outputs close to known answers y, for many examples (x, y). "Close" is measured by a loss L(θ), and training is minimising it:

θ* = argminθ  (1/N) Σi ℓ( f(xi; θ), yi )

dMapper's odometry already does exactly this kind of computation. In scan-to-map optimization, the unknowns are the window's poses, the "examples" are the points, and the loss is the sum of Mahalanobis distances of points to their NDT cells plus the prior terms; Levenberg–Marquardt then finds the minimum. The differences to machine learning are in scale and purpose:

dMapper scan-to-mapTraining a neural network
unknownsposes of one window (360 nodes × 6 ≈ 2 000 numbers)weights (hundreds to billions)
modelphysics: rigid motion, sensor geometrya generic flexible function, shape learned from data
lossNDT + IMU + prior termserror on training examples (+ regularisation)
solverGauss–Newton / Levenberg–Marquardt (second order)stochastic gradient descent, Adam (first order)
goalthe best poses for this datagood predictions on new, unseen data

The last row is the deep difference. dMapper wants the answer for the data in hand. Machine learning wants the parameters to work on data it has never seen. Everything about splitting data, overfitting and validation (T7) follows from that one requirement.

T2 · Linear models: the simplest learner

Linear regression predicts ŷ = wᵀx + b: a weighted sum of the features. With the squared error as loss, the minimum has a closed form, the normal equations (Xᵀ X) w = Xᵀ y, the same structure dMapper solves in every LM step (AᵀPA Δ = AᵀPb). No iteration is needed.

Logistic regression is the classification version: σ(wᵀx + b), with the sigmoid σ(z) = 1/(1 + e−z) squashing the sum into a probability between 0 and 1.

The limit: a linear model can only bend its output along straight directions in feature space. "The odometry error is large when the info ratio is low and the turn rate is high" is an interaction, which a sum can't express. You can add hand-made features (x₁·x₂, x²), but then you are designing the nonlinearity yourself. Neural networks learn it.

Why start with it anyway A linear model is the honest baseline. If a neural network can't beat it on held-out data, the problem is in the data or the features, not the model.

T3 · Neurons and networks, in arithmetic

A neuron computes a weighted sum of its inputs and passes it through a nonlinear activation function:

h = φ( w₁x₁ + w₂x₂ + … + wnxn + b )

Common activations: ReLU φ(z) = max(0, z), cheap and the default; tanh, smooth, between −1 and 1; sigmoid, between 0 and 1. Without φ, stacking layers would be pointless: a linear function of a linear function is still linear.

A layer is many neurons reading the same inputs, written as a matrix: h = φ(W x + b). A multi-layer perceptron (MLP) stacks layers:

h₁ = φ(W₁ x + b₁)  →  h₂ = φ(W₂ h₁ + b₂)  →  ŷ = W₃ h₂ + b₃

Counting parameters. A layer from n inputs to m outputs has n·m weights plus m biases. The point network of the roadmap, 10 → 32 → 16 → 1, has (10·32 + 32) + (32·16 + 16) + (16·1 + 1) = 352 + 528 + 17 = 897. A rule of thumb: with few examples, keep the parameter count well below the number of independent examples, or the network can memorise them.

Why this works at all. The universal approximation theorem says one hidden layer with enough neurons can approximate any continuous function on a bounded region. It says nothing about how many neurons, how much data, or whether training finds those weights. The theorem explains why networks are flexible, not why they generalise.

Initialisation. Weights start random, not zero: with zeros every neuron in a layer would compute the same thing and receive the same gradient forever. The usual scale for ReLU layers is a normal distribution with standard deviation √(2 / ninputs) ("He initialisation"), which keeps the size of the signals roughly constant from layer to layer.

T4 · Loss functions are likelihoods

The loss decides what the network learns, so it deserves more thought than the architecture. Most standard losses are negative log-likelihoods of a noise model, the same principle as the Mahalanobis terms in dMapper.

  • Mean squared error (y − ŷ)² is the negative log-likelihood of Gaussian noise with a fixed σ. It says: every example is equally reliable.
  • Gaussian negative log-likelihood with a predicted σ (heteroscedastic regression): the network outputs two numbers, a mean μ and log σ, and the loss is
    ℓ = (y − μ)² / (2σ²) + log σ
    The first term rewards a correct mean, weighted by 1/σ² like an information matrix. The second punishes claiming a large σ to excuse errors. At the minimum, σ matches the typical error. This is how a network learns "how uncertain am I here", which the roadmap needs for the window error predictor and the point weight. Predicting log σ instead of σ keeps σ positive without constraints.
  • Cross-entropy −[y log p + (1 − y) log(1 − p)] is the negative log-likelihood of a yes/no outcome. It is used for classification ("is this point noise?").
  • Robust losses (Huber, Cauchy) grow more slowly for large errors, so a few wrong labels can't dominate. They are the same idea as robust kernels in pose graphs and loop closure.

T5 · Gradient descent, and why not Levenberg–Marquardt

The gradient ∇L(θ) is the vector of ∂L/∂θk for every weight: the direction in which the loss rises fastest. Gradient descent takes a small step the other way:

θ ← θ − η ∇L(θ)

η is the learning rate. Too large, and the loss jumps around or explodes. Too small, and training crawls. It is the most important setting in training.

  • Stochastic gradient descent (SGD): instead of all N examples, each step uses a random minibatch (say 64). The gradient is noisy but N/64 times cheaper, and the noise even helps escape poor regions. One pass over all data is an epoch.
  • Momentum: keep a running average of past gradients and step along it, like a heavy ball rolling downhill. It smooths the noise and speeds up long valleys.
  • Adam, the usual default: momentum plus a per-weight step size, divided by the running root-mean-square of that weight's gradients. Weights with consistently large gradients get smaller steps, and rarely-active weights get larger ones. It is robust to the learning rate, which is why it is the default.
Why not the solver dMapper uses? Levenberg–Marquardt is second order: it builds the normal matrix JᵀJ, whose size is P × P for P unknowns. dMapper's window has a few thousand unknowns, and its matrix is banded, so this is cheap. A network with a million weights would need 10¹² matrix entries, and minibatch noise would make the curvature estimate unreliable anyway. First-order methods need only the gradient, which costs about as much as two or three forward passes (T6). For a tiny network (the 897-weight one) trained on the full dataset at once, second-order methods such as L-BFGS do work, and they are worth trying there.

A network's loss is not convex: there are many minima and flat regions, and the result depends on the random start. Train several times with different seeds and compare them, just as dMapper's s0/s1/s2 runs show the spread of the odometry.

T6 · Backpropagation: how the gradient is computed

Backpropagation is the chain rule of calculus, applied systematically. Take the 1-hidden-layer network from T3 with squared loss, for one example:

z = W₁x + b₁,   h = ReLU(z),   ŷ = W₂h + b₂,   L = (ŷ − y)²

The forward pass computes and stores z, h and ŷ. The backward pass starts at the loss and walks back, multiplying local derivatives:

∂L/∂ŷ = 2(ŷ − y)
∂L/∂W₂ = ∂L/∂ŷ · hᵀ    ∂L/∂b₂ = ∂L/∂ŷ
∂L/∂h = W₂ᵀ · ∂L/∂ŷ
∂L/∂z = ∂L/∂h ⊙ [z > 0]    (ReLU lets the gradient through only where it was active)
∂L/∂W₁ = ∂L/∂z · xᵀ    ∂L/∂b₁ = ∂L/∂z

Each step reuses the result of the step before. That is the whole trick: computing the gradient of all weights costs about two to three forward passes, no matter how many weights there are. Computing each derivative separately by finite differences would cost one forward pass per weight.

Gradient check. When you write backprop by hand, verify it numerically: change one weight by ±ε, and compare (L(θ+ε) − L(θ−ε)) / 2ε with your analytic derivative. They should agree to about six digits. This is the same central difference dMapper's window diagnostics use for the NDT stiffness.

T7 · Generalisation: why a perfect fit can be useless

A model with enough parameters can memorise its training data: zero training error, nonsense on new data. That is overfitting. The opposite, a model too simple to capture the pattern, is underfitting. You can only see which one you have on data the model never trained on.

  • Training / validation / test split. Train on one part. Choose settings (network size, learning rate, when to stop) on the validation part. Report the final quality once, on the test part. If you choose anything by looking at the test set, it stops being a test.
  • Cross-validation: with little data, rotate which part is held out (k folds) and average. In dMapper, the folds are recordings (leave one recording out).
  • Leakage is the classic way to fool yourself: information from the test set reaches training. With time series it happens silently. Neighbouring windows are almost identical, so a random split puts near-copies on both sides, and the model looks great because it recognises, not because it predicts.
  • Regularisation restrains the model:
    • weight decay adds λ‖θ‖² to the loss. In probability terms, it is a Gaussian prior on the weights, the same as dMapper's priors pulling a state toward its expected value;
    • early stopping: watch the validation loss during training, and stop when it starts to rise while the training loss still falls;
    • dropout: randomly switch off neurons during training, so no single neuron can be relied on.
  • Feature normalisation: scale each input to mean 0 and standard deviation 1 (with statistics from the training set only). Features on wildly different scales make the loss surface a long thin valley, the same ill-conditioning that unscaled normal equations suffer from, and gradient descent zigzags in it.
The bias–variance view The error on new data has two sources: bias (the model is too rigid to represent the truth) and variance (the model follows the noise of the particular training set). More parameters lower bias and raise variance; more data lowers variance. With little data, as in dMapper, variance dominates. That is why the roadmap prefers small models, strong baselines and honest splits.

What autograd does, behind the scenes

PyTorch records every operation you perform on tensors while the forward pass runs. This builds a computational graph: nodes are operations, and each one knows its own local derivative. Calling loss.backward() walks that graph in reverse, applying the chain rule of T6, and adds each weight's gradient into its .grad field. That is why every step starts with zero_grad(): otherwise the gradients from the previous step would be added on top. The graph is rebuilt on every forward pass ("define by run"), so ordinary Python if and for work inside a model.

The same 2-layer network, first by hand with numpy (every derivative written out, as in T6), then in PyTorch:

import numpy as np
rng = np.random.default_rng(0)
X = rng.normal(size=(500, 3))                      # 500 examples, 3 features
y = (np.sin(X[:, 0]) + 0.5 * X[:, 1] ** 2 + 0.1 * rng.normal(size=500))[:, None]

H, lr = 16, 0.05
W1 = rng.normal(scale=np.sqrt(2 / 3), size=(3, H)); b1 = np.zeros(H)   # He initialisation
W2 = rng.normal(scale=np.sqrt(2 / H), size=(H, 1)); b2 = np.zeros(1)
for step in range(2000):
    z1 = X @ W1 + b1                    # forward
    h1 = np.maximum(z1, 0)              # ReLU
    yhat = h1 @ W2 + b2
    loss = np.mean((yhat - y) ** 2)
    g_yhat = 2 * (yhat - y) / len(X)    # backward: chain rule, loss -> weights
    g_W2 = h1.T @ g_yhat; g_b2 = g_yhat.sum(axis=0)
    g_z1 = (g_yhat @ W2.T) * (z1 > 0)
    g_W1 = X.T @ g_z1;    g_b1 = g_z1.sum(axis=0)
    W1 -= lr * g_W1; b1 -= lr * g_b1; W2 -= lr * g_W2; b2 -= lr * g_b2    # gradient descent
    if step % 500 == 0:
        print(step, loss)
import torch
torch.manual_seed(0)
Xt = torch.tensor(X, dtype=torch.float32); yt = torch.tensor(y, dtype=torch.float32)
model = torch.nn.Sequential(torch.nn.Linear(3, 16), torch.nn.ReLU(), torch.nn.Linear(16, 1))
opt = torch.optim.SGD(model.parameters(), lr=0.05)
for step in range(2000):
    loss = torch.mean((model(Xt) - yt) ** 2)   # forward: records the graph
    opt.zero_grad()                             # clear the previous step's gradients
    loss.backward()                             # backward: autograd fills every weight's .grad
    opt.step()                                  # W -= lr * grad, for every weight

The derivative lines are gone. Now change the model so that it predicts its own uncertainty (T4). By hand, you derive and code new gradients for every layer. In PyTorch, only the loss changes:

model = torch.nn.Sequential(torch.nn.Linear(3, 16), torch.nn.ReLU(), torch.nn.Linear(16, 2))
out = model(Xt)
mu, log_sigma = out[:, :1], out[:, 1:]
loss = torch.mean(0.5 * ((yt - mu) / torch.exp(log_sigma)) ** 2 + log_sigma)   # Gaussian NLL

This is the real reason to use PyTorch: freedom in the loss and the model, at no cost in derivatives. scikit-learn's MLP can't take a custom loss like this one. Writing it by hand is the best way to learn backpropagation, but the slowest way to experiment.

The alternatives, briefly

  • TensorFlow / Keras: the same capabilities, with a heavier deployment ecosystem aimed at production servers and phones. PyTorch dominates research and teaching material, so examples and help are easier to find.
  • JAX: automatic differentiation of numpy-style pure functions, very elegant and fast, but more abstract. A good second framework, not a first.
  • ONNX: a file format for trained models, with runtimes for many languages. It is not needed in dMapper, because a small MLP's forward pass is about twenty lines of C++.

How a trained model reaches dMapper

Python is only for training. Once trained, the weights are plain numbers, written to a file and read by C++. The forward pass is a few loops. Written as plain loops, the sum runs in the same order every time, so a run gives the same bits as the last one:

// one hidden layer with ReLU; W1 is H x n (PyTorch's nn.Linear stores weights as out x in), W2 is 1 x H
double mlp(const Eigen::VectorXd &x, const Eigen::MatrixXd &W1, const Eigen::VectorXd &b1,
           const Eigen::RowVectorXd &W2, double b2)
{
    double out = b2;
    for (int j = 0; j < W1.rows(); j++)
    {
        double z = b1(j);
        for (int i = 0; i < W1.cols(); i++)
            z += W1(j, i) * x(i);
        out += W2(j) * std::max(z, 0.0);
    }
    return out;
}

Training needs PyTorch's machinery. Using the trained model needs only multiplication and addition.

T9 · Decision trees and gradient boosting

A decision tree asks a sequence of yes/no questions about the features ("info ratio < 0.3?", then "turn rate > 40°/s?") and predicts a constant in each leaf. Training picks, at each node, the feature and threshold that best separate the examples. Trees handle features on any scale and interactions naturally, but a single tree is crude and unstable.

Gradient boosting builds hundreds of small trees in sequence. Each new tree is fitted to what the trees so far still get wrong: for squared loss, literally their residuals; in general, the negative gradient of the loss, hence the name. Each tree's contribution is shrunk by a learning rate, so no single tree dominates. The sum is a strong, smooth-enough predictor.

  • Strengths: the best general method for small and medium tables of features, little tuning, and a ranking of feature importance that tells you what the model relies on.
  • Weaknesses: the output is piecewise constant (a staircase), with no gradient. It can't extrapolate beyond the training range, and it is harder to embed in C++ than an MLP, although still possible.

T10 · Bayesian optimization: tuning when each try is expensive

Tuning dMapper settings has an unusual shape: few knobs, no gradient, a noisy result, and each evaluation costs a full run. Grid search wastes runs, and random search ignores what it has learned. Bayesian optimization keeps a surrogate model of "quality as a function of the settings", built from the runs so far, and uses it to choose the next run.

  • Gaussian process surrogate: a probability distribution over smooth functions. After each run it gives, for any untried setting, a predicted quality and an uncertainty: small near tried settings, large far from them. The kernel encodes how smooth the function is assumed to be.
  • Acquisition function: scores each candidate by balancing exploitation (predicted good) against exploration (very uncertain, might be better). Expected improvement is the classic one: how much better than the best so far, on average, under the surrogate's uncertainty.
  • TPE (Optuna's default) works the other way round: it models the density of settings among good trials versus bad trials, and proposes settings that are likely under "good" and unlikely under "bad". It handles discrete and conditional settings well.

The result is typically a good setting in tens of runs instead of hundreds. Noise matters: if the run-to-run spread (s0/s1/s2) is as large as the differences between settings, the optimizer chases noise. That is why the gates require improvements beyond that spread.

T11 · Sequence models: memory over time

Windows come in a sequence, and what happened before matters. There are three ways to give a model that context:

  • Lagged features: append the previous windows' features to the input. Simple and transparent, and the right first choice with little data.
  • Recurrent networks (RNN, GRU, LSTM): carry a hidden state vector from step to step, ht = φ(W ht−1 + U xt + b), much like dMapper carries the gyro bias and velocity from window to window. Training backpropagates through all the steps ("through time"). Gradients then shrink or grow exponentially with the sequence length, which is the vanishing gradient problem. The LSTM and GRU add gates, small sigmoid layers that decide what to keep, forget and output, which let information and gradients survive many steps.
  • Transformers: no carried state. Every element looks at every other element through attention: it forms a query, compares it with all keys, and takes a weighted average of their values, softmax(QKᵀ/√d)·V. This is powerful for long-range patterns, but it needs a lot of data to learn which patterns matter. With a few thousand windows, a Transformer would mostly memorise.

T12 · Point cloud networks

A point cloud is a set: the same points in any order are the same scene. An ordinary MLP takes a fixed-length, ordered vector, so feeding it raw points makes no sense. Two answers:

  • PointNet: apply the same small MLP to every point separately (a "shared MLP"), then combine all points with a symmetric function, max-pooling over each feature, whose result doesn't depend on the order. Its weakness is that each point is seen alone before the pooling, so local structure (an edge, a corner) is captured poorly. PointNet++ applies PointNet to local neighbourhoods, and convolution-style networks such as KPConv learn local filters on points.
  • Hand-made local features: compute per point what the neighbourhood looks like, for example the eigenvalues of the neighbours' covariance. Linearity, planarity and scattering are ratios of these eigenvalues, so a wall, an edge and gravel look different. Feed them, with range, incidence angle and intensity, to a small per-point MLP. This is a "PointNet without pooling" on features you designed. It is cheap, deterministic, explainable, and needs far less data than learning the local structure itself.

Learned point networks shine with large labelled datasets and GPUs. With few recordings and no labels, the hand-made features are the right start. The networks are worth revisiting only if those features stop improving.

T13 · Reinforcement learning, and why it is so data-hungry

In reinforcement learning (RL), an agent observes a state, takes an action, receives a reward, and the world moves to a new state. The goal is a policy, a rule from state to action, that maximises the total reward over an episode. Applied to dMapper: the state is a window's telemetry, the action is a setting, the reward is map quality at the end, and an episode is one run.

Three difficulties make it expensive:

  • Credit assignment: the reward comes at the end. Which of 690 decisions made the map better?
  • Exploration: to learn that an action is good, it has to be tried, including bad ones, many times.
  • Your own data: the policy changes what it sees next, so old experience goes stale as it learns.

Typical RL successes use millions of episodes from a fast simulator. One dMapper episode is a 1.5–20 minute run.

A contextual bandit is RL with the hardest part removed: one decision, one reward, and no effect on later states. "Given these features, which of three settings?" is learnable with far less data, which is why the roadmap mentions it as the upper limit.

T14 · Uncertainty and calibration

A model that predicts σ, the window error predictor or the point weight, is only useful if its σ is calibrated: errors predicted at 2 cm should really be about 2 cm. Check it on held-out data:

  • z-scores: (y − μ)/σ over all examples should have mean ≈ 0 and standard deviation ≈ 1. A standard deviation of 2 means the model is overconfident by a factor of two.
  • Reliability plot: sort the examples by predicted σ into bins, and plot the observed RMS error per bin against the predicted σ. It should lie on the diagonal.

Calibration matters most when σ becomes a weight 1/σ² in dMapper's optimizer. An overconfident model gives some points or windows too much influence, exactly like a wrong sigma in the TOML.

Two kinds of uncertainty differ:

  • Aleatoric uncertainty: noise in the data itself. The heteroscedastic loss learns this.
  • Epistemic uncertainty: the model doesn't know because it has never seen such inputs, for example a cave after training on buildings. A model can't detect this from its own σ.

Epistemic uncertainty needs separate checks: inputs outside the training range, or the disagreement between several models trained with different seeds (an ensemble).

Phase 1 — Telemetry dataset started now as A2; the Python side later

Learn
Feature engineering, normalisation, the difference between causal features (known when the window is optimized) and non-causal ones (known only later).
Build

The other is the held-out planar thickness near each window. The script reports how far the two labels agree.
Done when
A table of ~690 rows for 44 (plus 46, s0/s1/s2) exists, and plots of correction against info ratio and turn rate show, or fail to show, the expected relation.

Phase 2 — Black-box tuning baseline no neural network

Learn
Bayesian optimization (a Gaussian-process or TPE surrogate plus an acquisition function), CMA-ES, multi-objective trade-offs, the noise of the objective (s0/s1/s2 spread).
Build
An Optuna driver that writes a TOML variant, runs dMapper CLI, and scores the result with map_quality.py and holdout_sharpness.py. Start with 3–6 global settings, chosen from those where earlier experiments have already shown an effect. Search on 44_short (~1.5 min per trial, 60 trials ≈ 1.5 h of runs), confirm the top 5 on full 44 s0/s1/s2 (~20 min each, ≈ 5 h), and then on 46. These times leave out scoring and any hold-out re-runs. map_quality.py is defined on full 44, so first check which of its metrics mean anything on 44_short; a setting that is best on the short cut may not be best on the whole recording. Done when
Either a settings change that clears the noise floor on 44, 46 and the cave's validation blocks, or the finding that the current settings are already near a local optimum. Both are useful results. (inference) The second is likely for settings already tuned by hand on 44, which is exactly why this baseline matters.

Phase 3 — First learned model: per-window error predictor diagnostic, changes no map

Learn
Regression with uncertainty (predicting a log-sigma, Gaussian negative log-likelihood), calibration plots, gradient-boosted trees against a small MLP, feature importance.
Build
Predict from the Phase-1 features how much each window's relative motion was corrected by loop closure and consistency. Use it first only to flag suspect windows in a report. That fits the planned map-quality-report, which needs to answer "where is my map weak" without ground truth.
What the label really measures. The pose graph and consistency spread accumulated drift over many windows by their weights. A window's correction is therefore a smoothed share of drift, not that window's own error, and a feature like "time since the last loop" may predict it better than any measure of a bad window. Windows with no loop get a correction near zero. That means "unobserved", not "good", so treat them as censored and leave them out of the training. Consistency uses the same NDT map and points, so it is not independent evidence. The label also changes whenever the loop-closure settings change. This is why the held-out thickness label from Phase 1 is kept alongside it.
Done when
On the test recording named on its card (a recording the model never saw, and each recording in turn left out), the model ranks windows better than the best single hand feature (for example the info ratio alone). If it doesn't, the features are wrong or the label is too noisy; fix that before Phase 4.

Phase 4 — Learned point weighting changes the map, off by default

Learn
Point-cloud features (eigenvalue shape features, incidence angle), heteroscedastic regression, robust losses, point-cloud networks (PointNet, KPConv) and why they are not the first choice here.
Build
A per-point MLP that predicts the expected distance σ of a point from the true surface. dMapper multiplies its NDT term by a weight derived from σ (for example 1/(1 + σ²/σ₀²), clamped). Label: the distance of each held-out point (holdout_block_s) to a plane fitted to the final map's points around it. This is a new script; holdout_sharpness.py measures surface thickness, not a per-point distance. Held-out points are never fitted, but the label is still not clean:
  • The final map was built by the current odometry, so the distance measures the trajectory's smear as much as the point's quality.
  • Down-weighting points far from the map pulls the map toward its majority, which can reinforce existing errors and penalise real but poorly mapped surfaces.
  • Hold-out mode leaves half the points out of the odometry, so the run that makes the labels is not the run that will use the model.
  • Incidence angle and distance to the matched cell depend on the current pose, so they change in every LM iteration and inherit the wrong cell normals (section 4).
Baseline to beat first: a hand-written weight on the incidence angle. Earlier experiments found grazing points cause about a fifth of the heading drift on 44, so the baseline already has a known target.
Done when
Trained on 44 and tested on 46, and the reverse (never trained and judged on 44 s0/s1/s2 alone, which are the same recording): holdout_sharpness.py and map_quality.py improve beyond the s0/s1/s2 spread, and the learned weight beats the incidence-angle rule. If only the rule helps, ship the rule.

Phase 5 — Per-window parameter policy changes the map, off by default

Learn
Contextual bandits, offline policy evaluation and its pitfalls (confounding, distribution shift), constrained outputs.
Build
A small model maps a window's features to a few bounded scale factors on sigmas and weights that are already per-window in the code. Its inputs must be known before the window is optimized: IMU values of the window itself, and the geometric and optimizer values of the previous window. The existing gated rule works the same way through carry.previous_window_degenerate. The hand-written competitor is the degeneracy-aware NDT projection (degenerate_projection_ratio 0.1 / _full 0.2), which is active in settings/l2-vertical.toml. The rule that raises a degenerate window's position sigmas runs only in the gated mode, and imu_always_on switches that mode off (run_odometry.cpp, acc_gated). Possible labels: repeat runs with a few global variants. For each window, the variant whose local quality was best (hold-out thickness near the window, size of the later correction) is the target. (inference) These labels are confounded, because a window's result depends on every window before it. Treat them as noisy and confirm with full runs.
Done when
It beats both the Phase-2 settings and the hand-written degeneracy rule on two recordings. It must also have been tried on a cave recording before it becomes a default.

Rules for the vector:

  • No absolute position, heading or time. They identify the recording, and the model would memorise where 44 is hard instead of learning why. Directions are expressed relative to gravity (vertical component) or as eigenvalue ratios, which don't depend on the heading.
  • Scale and normalise: logarithms of counts, rates and σs, then z-scores whose mean and std come from the training set and are stored in the model file. C++ must apply the same normalisation.
  • Causal for anything used inside the odometry: only values known before or during the window's optimization. Non-causal values (later correction, final map) may be labels, never inputs.
  • Out-of-range check: store the training range per feature. Outside it, the model returns the neutral output (scale 1) and the run logs a warning. (inference) A cave will produce values that 44 never showed.

Known trap in the cell statistics With use_exact_ndt_bucket_statistics = false (the default), a cell's mean is its first point. Its normal is fixed when the third point arrives, from those three points and the initial isotropic covariance. On a synthetic corridor 60 % of the normals are more than 30° off when the points are inserted in grid order, and 12 % in random order. Real scan order is neither (Degeneracy information). Shape and incidence features taken from the cells inherit that error. "Adaptive dropping in narrow passages", reconsidered

In a narrow passage the near walls supply most points, and the info ratio is already low. Dropping points there removes information exactly where it is scarce. (inference) The goals behind the idea — not letting one near wall dominate, and not trusting points while the gyro bias is uncertain — are better served by reweighting: a per-point weight (Phase 4), and per-window sigma scaling driven by the gyro-bias σ (Phase 5). Gyro drift is a rotation error. Fewer points don't fix it, but a better IMU prior or more geometric information does.

Splitting. Split by recording first (train on 44, test on 46, then the reverse). Within a recording, split into contiguous time blocks with a gap between them. 6. How a model enters dMapper

  • Domain: a SmallMlp value type (layer sizes, weights, activation, normalisation) with an evaluate() written as scalar loops in a fixed order, and unit-tested bit for bit against outputs exported from Python.
  • Ports in the domain: the per-point NDT term lives in lo_domain (scan_to_map.cpp), which cannot see lo_application. A PointWeightModel port therefore belongs in the domain, like Logger in run_reporting.h. Alternatively, weights or a weight function reach the optimizer through ScanToMapOptions. A WindowPolicy used by the window loop may live in the application. Each port has a neutral implementation (weight 1, scale 1), so the optimizer never knows whether a model is behind it.
  • Infrastructure: a JSON loader (vendored nlohmann json) that checks the model's feature list, sensor and numerics identifier, and refuses a mismatch.
  • Settings: a model path, empty by default, in a TOML section the odometry snapshot's settings hash covers. The hash must cover the model file's contents, not the path string. Otherwise renaming the file would invalidate snapshots, while changing its weights would not.
  • Results: the model's hash and numerics identifier in the results JSON and the parameter TOML, like gyro_bias_per_window today.
  • Cost: (inference) a 900-weight MLP costs about 1 800–2 000 floating-point operations per point. For 5·10⁷ point evaluations that is about 10¹¹ operations, roughly 10–100 s on one thread. It costs more if the weight is re-evaluated in every LM iteration, because incidence and cell distance change with the pose. Neighbour searches for the features cost more still. To be measured and reported, which is acceptable under "precision before speed".

7. Continuous learning without losing reproducibility (idea 4)

A model that learns during a mapping run would make the same input give different maps, and would break the golden baseline. "Continuous" therefore means a retraining cycle tied to the code's versions:

  • Retrain on every numeric change. A model trained on code with a bug learns to compensate for that bug. After the fix it over-compensates. Whenever new golden baselines are set, the dataset is regenerated and the model retrained. (inference)
  • Always compare three versions: no model, the previous model, and the retrained model. The no-model path stays the reference forever.
  • Watch the inputs: log the share of windows or points outside the training range per run. A rising share means the recordings have moved away from the training data, as a cave scan will.
  • Grow the dataset, not the model: each new recording (cave scans above all) is added to training, except for a fixed test part that is never trained on.
