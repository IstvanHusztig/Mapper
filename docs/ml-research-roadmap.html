Machine learning for dMapper: a research roadmap

A learning plan and research log, started 2026-10-27. It asks where small neural networks could make dMapper's maps more precise: per-window parameter tuning, adaptation to motion, point filtering, and a model that keeps up as the code changes. It covers what to learn first, which model fits which task, what the inputs are, and where the training data comes from. Statements marked (inference) are my own reasoning, not taken from a source or a measurement. The journal at the end records what was learned and decided, session by session.

In short Training waits; the data starts now. There is too little independent data to train anything trustworthy: two building recordings and no cave. A model trained today would fit those two buildings and be outdated by the next change to the numerics. But every scan and every run from now on can become learning data, if it is recorded with what training will need later. What cannot be recovered later is what was never recorded: how a scan was held, which code made a result, the odometry's own trajectory before loop closure replaced it. The direction now (track A): (1) every result records which code and build made it (commit, build settings, numerics epoch) and from which recording, not only 0.1.0; (2) every run writes per-window telemetry and the odometry's own window poses into the results JSON, so labels can be computed later; (3) every recording gets a card (sensor, unit, environment, how it was held, references) and a fixed role (train or test), decided when it arrives; (4) experiment folders keep their small files when the point clouds are deleted; (5) a general map-quality measure, the planned map-quality report, becomes the objective every later model is judged by. Models come later (track B), each unlocked by a data milestone, not a date: settings tuning with the cave retune, then an error predictor, a point weight and a window policy. Each is trained offline in Python, runs in C++ as deterministic Eigen code, is off by default, and is judged by the existing gates.

1. The ground rules that shape every choice

These come from the repository and decide more of the design than any ML textbook does.

2. Direction (question 1)

The learning runs as long as development does, so there is no deadline for a first model. What matters now is that the data the project produces anyway (new scans, test runs, experiments) is usable for training later. The work splits into two tracks:

  • track A starts now and needs no model and no new packages;
  • track B holds the model phases, each started only when its data exists.
The recordings are the lasting asset Run outputs can be regenerated. Rerunning a recording with the current build takes 1.5–20 min and gives telemetry that matches the current code, while telemetry from an old build describes numerics that no longer exist. So keep every recording, its original files and its card forever, with a backup copy. Old runs keep only their small files, as history. Regenerating is cheap for one feature table per recording, but not for label or variant runs: several recordings × variants × retrains is hours to days of runs, so those are planned as batches. Regenerating also needs to know how a run was made, which A1 records. (inference)

Track A — now: make every scan and run count

A1 — Provenance small code change

Today
A result records software_version (0.1.0, unchanged through many baseline refreshes), a settings-schema version and build_date (__DATE__, to the day). It cannot say which code made it, and it cannot say which recording it came from: only the output and preview folders are recorded.
Do
Add four things to the results JSON and the parameter TOML:
  • the code: the git commit, a "modified" flag, and a short hash of the diff when the tree is modified (experiments often run from modified trees or scratch worktrees);
  • the build: build type, floating-point mode (/fp:precise or /fp:fast) and HD_CPU_OPTIMIZATION, because the numerics depend on them;
  • a numerics epoch: a constant raised in the same commit that resets the golden manifests, so that each run can be assigned to a generation of the numerics, and later a model to the data it was trained on;
  • the recording: the id from its card (A3), or a hash of the input files' names and sizes, so that runs and cards can be joined.
Mechanics:
  • The stamp is made at every build, not once when CMake configures, or it goes stale.
  • compare_baseline.py normalises the commit keys, as it does build_date.
  • The golden TOML test files override them the way they set build_date = "GOLDEN".
  • A loaded TOML's values are replaced by the running build's, as build_date is today.

A2 — Window telemetry in the results JSON one OpenSpec change, numbers unchanged

Do
A window_telemetry block next to gyro_bias_per_window: per window, the features of section 4 and the odometry's start and end pose before loop closure and consistency. With these poses, the Phase-3 label (how much the window was corrected later) can be computed from the results JSON alone, without a snapshot reader. It stays out of the log and out of separate files, in keeping with "logging is console only". The odometry snapshot also holds these poses, but it is written only with save_odometry_snapshot = true, it is bound to the settings, and its format is binary. The JSON block is the portable record.
Cost
The information matrix behind the info ratio is computed today only in gated mode or with diagnostics on, so it would be computed in every run; measure the time. If the block is on in the shipped settings, the results JSON changes once, and the baseline manifests are reset in their own commit, with the numbers unchanged.

A3 — Recording cards and fixed roles no code

Do
A recording.json in each recording folder (dMapper ignores files that are neither LAZ/LAS nor CSV). It holds:
  • sensor, unit, and known faults (for example the L2 with the faulty gyro);
  • environment (building, cave, outdoors), route length, and how the sensor was held;
  • length of the static start, IMU synchronisation state, and conditions (dust, water, wet rock);
  • references (plan, tape or disto measurements);
  • a recording id; hashes of its files and where its backup copy lives;
  • its timestamp history: whether the IMU was restamped, with which tool and offset, and where the original file is kept;
  • firmware and calibration version of the unit;
  • a role: train, validation or test.
These facts are lost if they are not written down when the recording arrives. The role is decided then too, before any result has been looked at. One cave cannot be both: the cave retune needs the first cave recording. That recording is therefore validation, split into time blocks, for the few settings Phase 2 tunes. The test role starts with the second recording of a new kind, and that recording is never tuned on.
Why
Card fields become features (sensor, environment) and filters (faulty unit). A test role fixed in advance is the only protection against tuning on the test data without noticing.

A4 — Recording protocol for new scans no code

Do
For each new scan, at little extra effort:
  • a static start of 30–50 s;
  • at least one closed loop and deliberate revisits, since loop closure gives labels only where loops exist;
  • a few hand-measured distances or angles;
  • notes on the conditions;
  • now and then a deliberately hard stretch: a narrow passage, stairs, a chamber larger than the L2's 15 m range on dark rock.
Variety beats repetition: a new place teaches more than the same corridor twice. Most of this is already in the planned cave-recording task.

A5 — Run archive one script

Do
Before an experiment folder is deleted (test outputs are cleaned up regularly), copy its small files (parameter TOML, results JSON, map-quality output) to dLidar/run_archive/<recording>/<commit>_<label>/. The point clouds go, the record stays.
Why
Every experiment becomes a (code, settings, quality) row: the warm start for settings tuning, and a record of what was tried and why it failed.

A6 — A general objective already planned

Do
The planned map-quality report: revisits found automatically, doubled walls, surface thickness, and optional hand measurements, on any recording.
Why
Every learned component needs an objective that works on any recording, and map_quality.py is specific to recording 44 (the façade bands, its fixed revisit pairs, the Haus 47 plan). The objective matters more than the model. The ML track adds a reason for a feature that is already planned; it is not a new task.

A7 — Learning on the existing data continuous

Do
Work through the Phase-0 concepts. Then explore the existing data with numpy and matplotlib, which are installed: parse 44_diag.log (690 windows) and plot result − guess, iterations and info ratio along the route; check what moves together and what doesn't. Write one journal row per session. Learning to look at data comes before learning to fit it.
Not now No model hooks or ports in the C++ code until a model exists to fill them (no dead code). No model files, no ML packages, no tuning runs. A1–A6 are the only code and process changes, and A2 is the only one that touches the odometry's files.

Phase details (for when each phase starts)

Phase 0 — Foundations learning only

Learn
Linear and logistic regression, gradient descent, a 2-layer MLP and backpropagation (derive it by hand, then check it against a numerical gradient, the same central-difference trick log_weak_axis_diagnostics uses for the NDT stiffness); overfitting, regularisation (weight decay, early stopping), train/validation/test splits and leakage; gradient-boosted trees as a strong baseline on tabular data.
Build
Nothing in dMapper. Train toy models on the synthetic loop recording's outputs (tests/synthetic_recording), where the true trajectory is known, to practise the plumbing.
Tools
numpy, scipy, laspy are installed. Missing, to be installed when the phase needs them: python -m pip install --user scikit-learn lightgbm optuna and CPU PyTorch python -m pip install --user torch --index-url https://download.pytorch.org/whl/cpu.
Done when
You can explain why a model with 0.99 validation R² on randomly drawn windows can still be useless (neighbouring windows leak into each other).

Phase 1 — Telemetry dataset started now as A2; the Python side later

Learn
Feature engineering, normalisation, the difference between causal features (known when the window is optimized) and non-causal ones (known only later).
Build
The C++ side is A2: the window_telemetry block in the results JSON, with the features of section 4 and the odometry's own window poses. A setting that switches it goes into TomlIO::POINTERS and CATEGORIES, and the golden TOML files are regenerated in their own commit. Apart from the new block, the results must stay bit-identical. The Python side comes later, when Phase 3 starts: a script that joins the features with the labels. One label is the per-window correction between the odometry poses and the final trajectory. The other is the held-out planar thickness near each window. The script reports how far the two labels agree.
Done when
A table of ~690 rows for 44 (plus 46, s0/s1/s2) exists, and plots of correction against info ratio and turn rate show, or fail to show, the expected relation.

Phase 2 — Black-box tuning baseline no neural network

Learn
Bayesian optimization (a Gaussian-process or TPE surrogate plus an acquisition function), CMA-ES, multi-objective trade-offs, the noise of the objective (s0/s1/s2 spread).
Build
An Optuna driver that writes a TOML variant, runs dMapper CLI, and scores the result with map_quality.py and holdout_sharpness.py. Start with 3–6 global settings, chosen from those where earlier experiments have already shown an effect. Search on 44_short (~1.5 min per trial, 60 trials ≈ 1.5 h of runs), confirm the top 5 on full 44 s0/s1/s2 (~20 min each, ≈ 5 h), and then on 46. These times leave out scoring and any hold-out re-runs. map_quality.py is defined on full 44, so first check which of its metrics mean anything on 44_short; a setting that is best on the short cut may not be best on the whole recording. Feed the past hand-tuning results (openspec/changes/archive) in as known trials, but only those made with matching code.
Done when
Either a settings change that clears the noise floor on 44, 46 and the cave's validation blocks, or the finding that the current settings are already near a local optimum. Both are useful results. (inference) The second is likely for settings already tuned by hand on 44, which is exactly why this baseline matters.

Phase 3 — First learned model: per-window error predictor diagnostic, changes no map

Learn
Regression with uncertainty (predicting a log-sigma, Gaussian negative log-likelihood), calibration plots, gradient-boosted trees against a small MLP, feature importance.
Build
Predict from the Phase-1 features how much each window's relative motion was corrected by loop closure and consistency. Use it first only to flag suspect windows in a report. That fits the planned map-quality-report, which needs to answer "where is my map weak" without ground truth.
What the label really measures. The pose graph and consistency spread accumulated drift over many windows by their weights. A window's correction is therefore a smoothed share of drift, not that window's own error, and a feature like "time since the last loop" may predict it better than any measure of a bad window. Windows with no loop get a correction near zero. That means "unobserved", not "good", so treat them as censored and leave them out of the training. Consistency uses the same NDT map and points, so it is not independent evidence. The label also changes whenever the loop-closure settings change. This is why the held-out thickness label from Phase 1 is kept alongside it.
Done when
On the test recording named on its card (a recording the model never saw, and each recording in turn left out), the model ranks windows better than the best single hand feature (for example the info ratio alone). If it doesn't, the features are wrong or the label is too noisy; fix that before Phase 4.

Phase 4 — Learned point weighting changes the map, off by default

Learn
Point-cloud features (eigenvalue shape features, incidence angle), heteroscedastic regression, robust losses, point-cloud networks (PointNet, KPConv) and why they are not the first choice here.
Build
A per-point MLP that predicts the expected distance σ of a point from the true surface. dMapper multiplies its NDT term by a weight derived from σ (for example 1/(1 + σ²/σ₀²), clamped). Label: the distance of each held-out point (holdout_block_s) to a plane fitted to the final map's points around it. This is a new script; holdout_sharpness.py measures surface thickness, not a per-point distance. Held-out points are never fitted, but the label is still not clean:
  • The final map was built by the current odometry, so the distance measures the trajectory's smear as much as the point's quality.
  • Down-weighting points far from the map pulls the map toward its majority, which can reinforce existing errors and penalise real but poorly mapped surfaces.
  • Hold-out mode leaves half the points out of the odometry, so the run that makes the labels is not the run that will use the model.
  • Incidence angle and distance to the matched cell depend on the current pose, so they change in every LM iteration and inherit the wrong cell normals (section 4).
Baseline to beat first: a hand-written weight on the incidence angle. Earlier experiments found grazing points cause about a fifth of the heading drift on 44, so the baseline already has a known target.
Done when
Trained on 44 and tested on 46, and the reverse (never trained and judged on 44 s0/s1/s2 alone, which are the same recording): holdout_sharpness.py and map_quality.py improve beyond the s0/s1/s2 spread, and the learned weight beats the incidence-angle rule. If only the rule helps, ship the rule.

Phase 5 — Per-window parameter policy changes the map, off by default

Learn
Contextual bandits, offline policy evaluation and its pitfalls (confounding, distribution shift), constrained outputs.
Build
A small model maps a window's features to a few bounded scale factors on sigmas and weights that are already per-window in the code. Its inputs must be known before the window is optimized: IMU values of the window itself, and the geometric and optimizer values of the previous window. The existing gated rule works the same way through carry.previous_window_degenerate. The hand-written competitor is the degeneracy-aware NDT projection (degenerate_projection_ratio 0.1 / _full 0.2), which is active in settings/l2-vertical.toml. The rule that raises a degenerate window's position sigmas runs only in the gated mode, and imu_always_on switches that mode off (run_odometry.cpp, acc_gated). Possible labels: repeat runs with a few global variants. For each window, the variant whose local quality was best (hold-out thickness near the window, size of the later correction) is the target. (inference) These labels are confounded, because a window's result depends on every window before it. Treat them as noisy and confirm with full runs.
Done when
It beats both the Phase-2 settings and the hand-written degeneracy rule on two recordings. It must also have been tried on a cave recording before it becomes a default.

Phase 6 — Keeping the model current (idea 4) process

Learn
Dataset and model versioning, distribution-shift detection, why "online learning" during a mapping run conflicts with reproducibility.
Build
A retraining script tied to the baseline procedure. Whenever a change sets new golden baselines, regenerate the dataset with the new build, retrain, and compare three versions on the gates: no model, the old model, and the retrained model. Record the model hash, the dataset hash and a numerics identifier in the model file and in the results JSON. The numerics identifier is the hash of the golden manifest (tools/baseline/44.manifest.json) the model was trained against. The dMapper version is not enough: it stayed 0.1.0 through many baseline refreshes.
Done when
Retraining is one command, and a model trained against a different numerics identifier is refused, or at least warned about.

Working with Claude through the phases

  • Learn on this code base, not on toy data alone. Ask for the concept and then for where it appears in dMapper. The NDT cost is a negative log-likelihood, the LM iterations are second-order optimization, and the gyro-bias prior is Bayesian updating. Many ML ideas are already in the optimizer under other names.
  • One OpenSpec change per phase that touches C++ (/opsx:propose), with the gates in its tasks, the same as for any other change.
  • Effort level: high for the design and for interpreting results (Phases 3–5), medium for the exporter, the training scripts and the run batches.
  • Long batches (Optuna trials, full 44 runs) run as one background script that reports only its final tables, the same as the current run batches.
  • Review: each conclusion ("the model helps", "feature X matters") is checked by a review agent against the numbers before it goes into the journal.
  • This page is the journal. At the end of each session, add a row to section 8: what was tried, the numbers, what was decided.

3. Which model for which job (question 2)

The data size decides most of this. With roughly a thousand windows and strong correlation between neighbours, a model with a million parameters will memorise. Tens of thousands of points per window do give enough rows for small per-point models.

Rules for the vector:

  • No absolute position, heading or time. They identify the recording, and the model would memorise where 44 is hard instead of learning why. Directions are expressed relative to gravity (vertical component) or as eigenvalue ratios, which don't depend on the heading.
  • Scale and normalise: logarithms of counts, rates and σs, then z-scores whose mean and std come from the training set and are stored in the model file. C++ must apply the same normalisation.
  • Causal for anything used inside the odometry: only values known before or during the window's optimization. Non-causal values (later correction, final map) may be labels, never inputs.
  • Out-of-range check: store the training range per feature. Outside it, the model returns the neutral output (scale 1) and the run logs a warning. (inference) A cave will produce values that 44 never showed.

Known trap in the cell statistics With use_exact_ndt_bucket_statistics = false (the default), a cell's mean is its first point. Its normal is fixed when the third point arrives, from those three points and the initial isotropic covariance. On a synthetic corridor 60 % of the normals are more than 30° off when the points are inserted in grid order, and 12 % in random order. Real scan order is neither (Degeneracy information). Shape and incidence features taken from the cells inherit that error. Compute them from a neighbour search for training, and measure how much worse the cell-based version is before using it inside the odometry.

"Adaptive dropping in narrow passages", reconsidered

In a narrow passage the near walls supply most points, and the info ratio is already low. Dropping points there removes information exactly where it is scarce. (inference) The goals behind the idea — not letting one near wall dominate, and not trusting points while the gyro bias is uncertain — are better served by reweighting: a per-point weight (Phase 4), and per-window sigma scaling driven by the gyro-bias σ (Phase 5). Gyro drift is a rotation error. Fewer points don't fix it, but a better IMU prior or more geometric information does.

Splitting. Split by recording first (train on 44, test on 46, then the reverse). Within a recording, split into contiguous time blocks with a gap between them. Never split randomly by window or point: neighbours are almost copies, and a random split reports accuracy that will not hold on a new recording. Two limits remain. Two similar buildings give only two folds, so every score has a large uncertainty; report both folds, not their mean. And a recording that revisits places (44 does) shows the same walls on both sides of a time split, so add a spatial split (by floor or by region) where the route allows it.

From manual tuning to automated training. Hand tuning (each archived OpenSpec experiment) gives starting points for Phase 2. Phase 2 gives settings and a cost surface. Phases 3–5 add per-window and per-point models on top of the best global settings. They are judged by whether they beat the global settings, never against the old defaults.

6. How a model enters dMapper

  • Domain: a SmallMlp value type (layer sizes, weights, activation, normalisation) with an evaluate() written as scalar loops in a fixed order, and unit-tested bit for bit against outputs exported from Python.
  • Ports in the domain: the per-point NDT term lives in lo_domain (scan_to_map.cpp), which cannot see lo_application. A PointWeightModel port therefore belongs in the domain, like Logger in run_reporting.h. Alternatively, weights or a weight function reach the optimizer through ScanToMapOptions. A WindowPolicy used by the window loop may live in the application. Each port has a neutral implementation (weight 1, scale 1), so the optimizer never knows whether a model is behind it.
  • Infrastructure: a JSON loader (vendored nlohmann json) that checks the model's feature list, sensor and numerics identifier, and refuses a mismatch.
  • Settings: a model path, empty by default, in a TOML section the odometry snapshot's settings hash covers. The hash must cover the model file's contents, not the path string. Otherwise renaming the file would invalidate snapshots, while changing its weights would not.
  • Results: the model's hash and numerics identifier in the results JSON and the parameter TOML, like gyro_bias_per_window today.
  • Cost: (inference) a 900-weight MLP costs about 1 800–2 000 floating-point operations per point. For 5·10⁷ point evaluations that is about 10¹¹ operations, roughly 10–100 s on one thread. It costs more if the weight is re-evaluated in every LM iteration, because incidence and cell distance change with the pose. Neighbour searches for the features cost more still. To be measured and reported, which is acceptable under "precision before speed".

7. Continuous learning without losing reproducibility (idea 4)

A model that learns during a mapping run would make the same input give different maps, and would break the golden baseline. "Continuous" therefore means a retraining cycle tied to the code's versions:

  • Retrain on every numeric change. A model trained on code with a bug learns to compensate for that bug. After the fix it over-compensates. Whenever new golden baselines are set, the dataset is regenerated and the model retrained. (inference)
  • Always compare three versions: no model, the previous model, and the retrained model. The no-model path stays the reference forever.
  • Watch the inputs: log the share of windows or points outside the training range per run. A rising share means the recordings have moved away from the training data, as a cave scan will.
  • Grow the dataset, not the model: each new recording (cave scans above all) is added to training, except for a fixed test part that is never trained on.
